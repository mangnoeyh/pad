# 근거를 확인하며 최소 수정하기

작업 지침과 확정된 정책을 유지한다. AI 이용이 제한되는 후속 절차에는 적용하지 않는다. 목표는 실패를 숨기는 것이 아니라 원인을 확인하고 필요한 동작을 복구하는 것이다.

이 지침은 이미 동의한 작업 단위 안에서만 적용한다. 이해 확인이나 중요한 결정에 대한 사용자 답을 기다리는 동안 다음 단계 구현을 진행하지 않는다. 남은 시간과 합의한 반복 한도를 지키며 모델·추론 설정을 자동 변경하지 않는다.

## 1. 재현과 원인 조사

- 실제 명령·입력·전체 오류·종료 상태를 확인한다. 직접 실행한 결과와 사용자가 전달한 로그를 구분한다. 민감한 값이나 전체 환경 변수를 로그에 노출하지 않는다.
- 가능한 가장 작은 재현을 만든다. 재현되지 않으면 미재현이라고 표시하고 관측을 추가한다.
- 최근 수정, 관련 코드, 정상 동작 사례, 설정·런타임 차이를 비교한다. 파일이나 패키지가 존재한다고 가정하지 않는다.
- 복잡한 흐름은 입력부터 실패 지점까지 추적한다. 필요한 경계에만 진단 정보를 추가하며 무관한 시스템 정보를 수집하지 않는다.

## 2. 가설 하나씩 검증

'가설 / 근거 / 이를 반박할 관측 / 최소 확인 방법'을 짧게 정리한다. 가설이 확인되지 않았는데 원인을 확정했다고 말하지 않는다.

한 번에 여러 설정과 의존성을 바꾸지 않는다. 새 증거가 없는데 같은 수정이나 명령을 반복하지 않는다. 반복 실패하면 확인된 사실과 버린 가설을 정리하고 진단 방법을 바꾼다. 실패 횟수만으로 아키텍처가 틀렸다고 단정하지 않는다.

## 3. 수정

- 합의한 범위의 오류는 매번 승인받지 않고 최소 수정한다. 관련 없는 기능 추가와 정리를 섞지 않는다.
- 업무 정책, 중요한 기술 선택, 필수 기능 범위, 큰 의존성을 변경해야 한다면 이유·영향·대안을 사람이 판단하도록 제시한다. 이미 위임한 범위는 다시 묻지 않는다.
- 가능하면 먼저 회귀 테스트나 재현 스크립트로 실패를 확인한다. 테스트 도구가 없으면 제공 런타임의 작은 검증 스크립트를 사용할 수 있다. 새 테스트 프레임워크 설치를 자동으로 요구하지 않는다.
- 테스트를 통과시키려고 기대값을 현재 구현에 맞추거나 실패 검사를 제거하지 않는다. 테스트가 명세와 충돌한다면 근거를 확인하고 업무 해석이 필요한 부분만 사람에게 묻는다.
- 수정 전 실패를 직접 확인하지 못한 경우 그 한계를 기록한다. 이미 작성한 정상 코드를 테스트 우선 원칙 때문에 삭제하지 않는다.

## 4. 재검증과 보고

원래 실패를 재검증하고 영향을 받는 기존 검사를 수행한다. 최종 수정 이후 결과를 사용한다. 원인이 외부 서비스나 실행 환경이라면 코드 결함과 구분하고, 제한을 우회하거나 제공 Codex를 업데이트하지 않는다. 플랫폼 문제 접수에 필요한 발생 시각·증상·재현 단계를 정리해 사람이 전달하도록 한다.

보고는 다음 순서를 따른다.

1. 관측된 문제와 재현 여부.
2. 확인된 원인 또는 아직 미확정인 가설.
3. 변경 파일과 변경 이유.
4. 실제 실행한 검증, 결과, 남은 실패·미검증.
5. 다음 행동과 사람의 결정이 필요한 항목.

'코드 변경 완료', '특정 검사 통과', '과제 전체 완료'를 구분한다. 다른 스킬, 외부 서비스, 서브에이전트 없이도 이 절차를 수행한다.
