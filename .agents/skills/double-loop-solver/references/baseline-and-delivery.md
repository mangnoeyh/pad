# 요구 변경에서 기준본과 전달본까지

이 참고안은 기존 작업 메모나 양식에 필요한 판단과 근거를 남기는 데 쓴다. 별도 문서나 도구 도입을 요구하지 않는다.

## 1. 이해와 결정의 경계
- 처음에는 입력, 사용자 역할, 필수 동작, 결과물, 실행 환경을 함께 짚어 이해를 맞춘다.
- 범위·품질·데이터 처리처럼 결과를 바꾸는 중요한 선택은 사람이 결정하거나 사전 위임한 범위에서 처리한다. 합의한 작업 단위 안의 통상 명령마다 새 승인을 받지는 않는다.
- 반복 운영할 서비스를 만드는 과제라면 최종 결과물은 개발자가 한 번 계산해 준 해가 아니라, 운영자가 허용된 설정·데이터를 바꾸고 재계산할 수 있는 서비스다. 개발 중 사람과 메인 에이전트가 일반 판정 기준, 정책 완화 순서, 적용 범위·한도와 실패 처리를 합의하고 구현한다. 통상 운영에서 새 대상마다 개발자 LLM이나 사람에게 예외 승인을 받도록 만들지 않는다.
- 요구마다 근거, 적용 입력·후보, 상태(활성/대기/철회)를 기록하고 **출처와 집행 방식을 별개 축**으로 구분한다.
  - 출처: 과제 원문·산출물 명세·규정·계약에서 온 요구인지, 사용자가 추가한 정책인지, 작업을 위한 구현 가정인지 실제 근거를 구분한다. 출처만으로 모든 요구의 집행 방식을 같게 취급하지 않는다.
  - 집행 방식: 반드시 충족할 조건, 더 좋은 결과를 위한 목표, 예외가 없을 때 적용할 기본값. 과제에 명시된 필수 제약은 사용자 정책의 예외 승인만으로 완화하지 않는다. 사용자 정책도 현재 반드시 충족할 조건일 수 있으나, 사용자가 범위를 정해 예외·완화·철회를 결정할 수 있다. 목표나 기본값을 임의로 강제 조건으로 올리지 않는다.
  - 매개변수: 과제가 운영자 조정을 허용한 필수 제약은 허용 범위와 현재 적용값을 구분한다. 검증은 기본 상수가 아니라 해당 실행에 적용된 정당한 설정값을 따른다. 권한 있는 운영자의 허용된 변경은 솔버의 임의 완화가 아니며, 솔버가 설정값을 몰래 바꾸는 것은 허용하지 않는다.
  - 구현 가정에는 확인 주체와 영향 범위를 붙인다. 해석이 미정인 요구를 확정된 과제 필수 제약으로 취급하지 않는다.
- 변경 시 이전 내용과 새 내용, 적용 범위, 결정 주체·승인 또는 위임 근거를 기존 메모에 남긴다. 예외는 해당 범위에만 적용하고, 철회한 조건은 현재 조건으로 계산하지 않는다. 나머지 사용자 정책과 모든 과제 필수 제약은 유지한다.

## 2. 확장 전에 가능한지 확인
- 선택적 범위 확장이나 사용자 정책을 강제 조건으로 채택하기 전에 필요한 저비용 확인부터 한다.
- 해당 입력에서 실제 후보가 있는지, 전체·그룹별 용량의 상하한이 맞는지, 조건끼리 충돌하는지 확인한다. 적용되지 않는 검사는 생략한다.
- 결과를 다음처럼 구분한다.
  - 입력·설정 오류: 스키마, 참조 관계, 값의 형식 또는 허용 범위를 어겨 실행 계약에 맞지 않는다. 수정할 항목을 제시한다.
  - 불가능 입증: 유효한 입력·설정에 대해 필요조건 실패나 타당한 증명으로 해당 정책 범위에서 해가 없음을 확인했다. 근거와 범위를 남긴다.
  - 탐색 미해결: 아직 유효한 해를 찾지 못했거나 시간·자원 한도로 중단했다. 불가능 판정이 아니다.
  - 완전 유효한 해 확보: 현재 적용 설정에 따른 과제 필수 제약, 승인된 정책·예외를 반영한 사용자 강제 조건, 전체 요구 범위를 만족하는 결과를 검증했다. 목표 달성도는 별도로 비교한다.
- 필요조건 통과만으로 해 존재를 보장하지 않는다. 임의의 모든 데이터·설정 조합을 풀 수 있다고 약속하지 않는다.
- 부분 처리·미배정이 늘거나 기준본보다 성능이 나쁜 후보도 거절로 끝내지 않는다. 제한을 표시한 실험으로 보존하고, 입증된 제약 충돌과 탐색 방식·실행 시간·후보 부족으로 아직 풀지 못한 경우를 구분한다.
- 충돌하거나 결과를 악화시키는 사용자 정의 조건을 좁혀, 최소 범위의 예외·완화·철회와 입력 보완·탐색 개선을 비교한다. 과제 필수 제약을 완화 후보로 제시하지 않는다. 각 대안의 예상 회복량, 비용과 불확실성을 적고 가능하면 전체 재실행으로 측정한다. 추정치와 측정치를 구분한다.
- 개발 중 정책 밖의 대안은 사용자가 선택하고, 기존 위임 범위 안의 대안은 그 기준에 따라 적용한다. 운영 중에는 사전 합의한 정책으로 자동 처리하며 매 실행 승인을 요구하지 않는다. 사전 승인 없는 가정적 완화 결과는 실험으로 남기되, 승인된 예외까지 항상 전달 불가로 취급하지 않는다.

## 3. 범위가 있는 예외와 공동 검증
- 예외마다 바꿀 사용자 조건, 적용 대상·날짜·방향 등 해당 과제의 범위, 발동 조건, 적용 단위, 승인 근거를 명시한다. 예를 들어 지정 대상의 포함 여부로 발동해 그 대상이 속한 그룹 전체에 적용할 수 있다. 발동 대상과 실제 예외 적용 범위는 구별한다.
- **수동 고정 목록**과 **승인된 규칙에 따른 동적 자격 판정**을 구분한다. 고정 목록 예외는 명시한 대상에만 적용한다. 규칙 기반 예외는 판정 조건·범위·한도를 정책으로 승인받고, 입력·설정·정책 버전마다 자격을 다시 계산한다. 규칙에 새로 부합한 대상은 별도 개별 승인 없이 포함한다. 과거 실행에서 선택한 대상 목록을 다음 실행의 일반 규칙 대신 하드코딩하지 않는다.
- 그룹 소속에 따라 발동하는 예외는 각 전체 재실행의 **최종 배정**에서 조건을 다시 계산한다. 이전 실행의 그룹 식별자나 구성원을 고정하지 않는다. 적용 집합이 바뀌면 그 결과와 예외 판정이 함께 일치하는지 다시 검증한다.
- 미배정·미처리가 새로 발생했다는 이유만으로 승인된 정책 밖까지 예외를 확대하지 않는다. 반대로 그 대상이 승인된 동적 규칙에 부합하면 자동 적용한다. 정책 범위 안에서 해결하지 못하면 근거에 따라 불가능 입증과 탐색 미해결을 구분해 보고하며, 운영 중 임의 면제나 개발자 호출로 메우지 않는다.
- 여러 예외는 함께 적용한 전체 결과로 검증한다. 개별 실험의 회복량을 더해 공동 효과로 주장하지 않는다. 공유 용량 경쟁, 대상의 중복 회복, 다른 대상의 새 미처리와 나머지 조건 위반을 확인한다.
- 기준본 대비 순회복량과 새 미처리, 비용·품질 변화, 예외 수·적용 규모·완화 정도를 함께 제시한다. 사용자가 정하지 않은 예외 수 상한이나 심각도 임계값을 새 강제 조건으로 만들지 않는다.
- 실제 시간·자원 한도 안에서 탐색을 제한하고, 현재 조건에서 가장 좋은 검증된 안정안과 유망한 실험안을 함께 남긴다. 남은 불확실성과 다음에 확인할 비교가 무엇인지 명시한다.

## 4. 서비스의 자율 재계산
- 전원 처리 같은 필수 범위를 선택적 사용자 선호가 의도치 않게 막지 않도록 개발 중 일반 기준을 설계한다. 선호를 목표·기본값으로 둘지, 어떤 조건에서 어느 순서로 완화할지, 전체 범위를 회복할 수 있는 대체 경로와 그 한도를 정한다. 전체 범위를 만족하는 해끼리 성능을 비교하며, 빠르거나 점수가 좋다는 이유로 미처리 결과를 더 좋은 해로 채택하지 않는다.
- 재계산은 **입력·설정·정책 스냅샷 → 기본 계획 → 미처리·충돌 진단 → 정책 범위 안의 제한된 복구·완화 → 전체 검증 → 원자적 적용과 보고**로 이어진다. 복구는 승인된 순서·발동 조건·자원 한도를 따르고, 과제 필수 제약과 정책의 최종 한계 밖으로 진행하지 않는다. 허용된 복구를 소진하면 구분된 실패·미해결 상태를 반환한다.
- 이전 전원 처리 결과나 대체 경로도 현재 입력·설정·정책으로 다시 검증해야 한다. 현재 제약을 위반하는 과거 결과를 성공한 대체 해로 사용하지 않는다.
- 전체 검증에 성공한 결과만 한 번에 적용한다. 계산 도중 스냅샷의 입력·설정·정책이 바뀌었으면 낡은 후보의 적용을 막고 최신 버전으로 재계산하거나 재계산 필요 상태를 표시한다.
- 실패하면 기존 적용 결과를 보존하되 그 결과의 버전과 **이전 결과** 상태를 명시한다. 최신 요청의 성공 결과로 표시하지 않는다. 실행 상태, 현재 요청 버전, 적용 결과 버전, 사용한 완화 단계·범위와 남은 미처리를 구분해 보고한다.

## 5. 작은 전체 경로와 재현 가능한 기준본
- 필수 입력부터 필수 결과까지 이어지는 가장 작은 전체 경로를 일찍 만든다.
- 기준본에는 다시 만들 수 있는 소스, 설정, 실행 진입점, 입력 또는 입력 계약, 결과와 검증 근거를 함께 고정한다.
- 이미 떠 있는 이전 프로세스나 데이터 저장소의 해시만으로 다시 만들 수 있다고 판단하지 않는다.
- 소스 스냅샷 → 빌드 → 실행 → 데이터·설정 → 결과·출력 → 전달물의 대응 관계를 기존 메모에 연결한다.
- 실제로 요구되는 구성요소만 다룬다. 컨테이너, 버전 관리, 데이터 저장소, 프레임워크나 새 기록 체계를 일괄 요구하지 않는다.
- 부분 구현, 일부 입력만 다룬 후보, 미승인 조건 완화 또는 과제 필수 제약 위반 후보는 그 제한을 표시하고 유효한 기준본·전달 후보와 분리한다.
- 사용자 정책의 예외·완화가 승인되거나 기존 위임 범위에 있고, 모든 과제 필수 제약과 변경 뒤 남은 강제 조건·요구 범위를 전체 검증한 후보는 기준본·전달 후보로 승격할 수 있다. 목표 달성도와 승인 내용, 검증 버전을 함께 남긴다.
- 조건이 바뀌면 이전 기준본도 새 조건으로 다시 검증한다. 이전 검증만으로 현재 조건 충족을 주장하지 않는다.

## 6. 비용과 남은 작업 판단
- 입력 준비, 구현, 전체 검증, 통합, 전달 여유를 모두 포함해 비용을 다시 추정한다.
- 실제 입력 규모와 측정된 처리 시간, 수정량, 미확인 의존성, 변동 폭을 근거로 추정 범위와 불확실성을 적는다.
- 작은 입력의 빠른 실행을 전체 검증 비용으로 대신하지 않는다. 측정할 수 없는 부분은 미측정으로 표시한다.
- 실제 주어진 기한만 사용한다. 임의 기한, 고정 일정이나 시간 배분 비율을 만들지 않는다.
- 남은 자원으로 완료할 수 있는지 보고 선택적 개선을 조정한다. 과제 필수 제약은 유지하고, 사용자 정책의 조정은 승인 또는 기존 위임 범위 안에서만 반영한다.

## 7. 전달 후보 승격과 실행 확인
- 승격 전 모든 과제 필수 제약, 승인된 예외·완화·철회를 반영한 현재 사용자 조건, 요구된 범위와 사용자가 합의한 범위를 대조한다. 정책 변경 전후의 품질·비용·미처리·예외 영향을 함께 제시한다.
- 예외의 승인만으로 검증을 대신하지 않는다. 최종 배정에서 예외 발동·적용 범위를 다시 확인하고 나머지 조건과 공동 효과를 전체 검증한다. 미승인 가정적 완화나 과제 필수 제약 위반은 실험 상태로 남긴다.
- 오프라인 실행 지시 등 환경 제한은 계속 지킨다. 외부 연결로 검증을 대신하지 않는다.
- 문서화된 깨끗한 시작 절차를 격리된 사본에서 실행한다. 운영 데이터 삭제로 초기 상태를 만들지 않는다.
- 적용되는 실제 흐름만 확인한다: 필수 입력, 변경, 재계산, 실패 시 기존 데이터 보존, 역할별 조회, 내보내기, 재시작.
- 반복 운영 서비스는 기존 대상뿐 아니라 새 입력에서 규칙에 새로 부합하는 대상, 허용된 설정 변경, 정책 밖의 대상과 복구 한도 도달, 현재 설정에서 무효가 된 이전 결과를 확인한다. 개별 개발자 개입 없이 재계산·전체 검증·상태 보고가 이어지는지 검증한다.
- HTTP 응답 확인과 사람이 화면에서 수행하는 확인은 구별한다. 한쪽 결과로 다른 쪽까지 확인했다고 쓰지 않는다.
- 최종 확인은 전달할 바로 그 후보의 소스·빌드·설정·입력으로 수행하고 버전을 고정한다.
- 고정 뒤 변경하면 영향받는 근거를 재확인 필요로 표시하고 남은 자원 안에서 다시 확인한다. 미확인 항목은 전달 상태에 드러낸다.
- 사용자에게 설명하는 입력 → 처리 → 저장·표시·출력 흐름도 같은 버전에 맞춘다.
- 제안됨, 구현됨, 검증됨, 실제 환경에 적용됨, 전달됨을 각각 구분한다. 전달 위치와 실행 방법이 확인된 상태로 마무리한다.
