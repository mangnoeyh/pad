# 구현과 검토의 진행 기준

이 문서는 상황에 맞게 적용하는 참고 기준이다. 현재 사용자가 지정한 정지 지점이나 허용 범위를 넓히지 않는다.

## 기존 구현을 바꿀 때

- 기존 코드 수정이라면 먼저 관련 파일과 현재 검증 결과를 기록한다. 변경 전후에 같은 명령과 조건을 사용한다.
- 이미 있던 실패, 새로 생긴 회귀, 환경 때문에 실행하지 못한 검사를 구분한다. 기존 실패를 수정 결과로 포장하지 않는다.
- 먼저 핵심 입력이 원하는 출력까지 도달하는 최소 동작 경로를 만든다. 확장은 합의한 작업 단위 안에서 진행한다.

## 실패를 확인하는 검증

- 실패 조건 검사는 의도한 분기까지 도달했음을 확인한 뒤 기대한 실패의 종류와 내용을 검사한다.
- 예를 들어 업무 규칙 거절을 확인하는 사례가 인증 실패나 자료형 오류로 끝났다면 통과로 처리하지 않는다.
- 실패 시 상태 보존이 계약에 포함된다면 호출 전후 상태를 비교해 부분 변경이 남지 않았는지 확인한다.
- 검증 근거는 실제 요구 계약과 연결한다. 허용된 기존 기술 구성을 개인적인 구조나 스타일 선호로 결함 처리하지 않는다.

### 핵심 검사가 결함을 잡는지 확인할 때

테스트의 민감도가 의심되거나 핵심 조건의 검증 신뢰도가 중요하면, 합의한 예산 안에서 작은 결함 하나로 확인할 수 있다. 직접 작성한 구현의 격리된 사본에서만 알려진 검증 누락이나 경계 오류를 임시로 만들고, 관련 검사가 의도한 이유로 실패하는지 본다. 제공 원본·공식 검사 기대값·공유 실행 서비스를 이 실험으로 바꾸지 않는다.

정상본 통과 → 결함 사본의 예상 실패 → 원상 복구·정상본 재통과를 구분해 기록하고, 원본 해시나 diff로 복원을 확인한다. import 오류·환경 장애로 끝난 실행을 의도한 결함 탐지로 계산하지 않는다. 결함을 넣어도 검사가 통과하면 확인 범위나 기대값을 재검토한다. 전체 테스트 품질을 보장한다고 확대하지 않으며, 모든 작업마다 강제하거나 새 도구를 설치하지 않는다.

## 실행 중인 버전과 충돌

- 디스크에 저장된 코드, 편집기의 미저장 내용, 이미 실행 중인 서버가 읽은 버전을 구분한다.
- 내용이 충돌하면 양쪽을 읽고 복구 가능한 형태로 보존한 뒤 선택한다. 한쪽을 확인하지 않고 덮어쓰지 않는다.
- 선택이나 재시작 후에는 영향을 받는 검사를 다시 실행한다. 화면 확인이 필요한 부분은 허용된 수단으로 재확인하거나 수동 확인 항목으로 남긴다.

## 병렬 작업이 실제로 가능한 경우

큰 독립 작업의 역할·모델·추론 수준 분담은 [병렬 작업 기준](parallel-work.md)을 적용한다. 실제 사용 가능한 모델과 위임 인수 범위 안에서 선택하며, 주 세션의 설정 변경과 워커별 선택을 구분한다.

- 제공된 기능으로 독립 작업을 나눠 이득이 있을 때만 사용하고, 없으면 같은 단위를 순서대로 수행한다. 새 세션·플러그인·설정 변경을 전제하지 않는다. 모든 작업은 현재 합의한 단위와 대기 지점을 지킨다.
- 맡길 목표, 수정 가능한 파일, 입력·출력, 완료 확인 방법을 먼저 정한다. 같은 파일은 한 작업만 수정하고, 검토 역할은 읽기 전용으로 둔다.
- 공유 설정·의존성·서버·통합 기록은 주 작업자가 관리한다. 각 작업의 임시 파일·데이터베이스·포트는 충돌하지 않게 분리한다.
- 결과가 돌아오면 실제 변경 범위를 확인하고 통합된 현재 상태에서 영향을 받는 완료 검사를 다시 실행한다. 작업자의 완료 보고만으로 검증 완료를 기록하지 않는다.
- 다른 작업이 남아 있는 공유 폴더에서는 필요한 경로만 스테이징하고, 다른 사람의 변경을 지우거나 함께 포함하는 전체 정리·초기화 명령을 사용하지 않는다.

## 근거를 분류하거나 계산할 때만

- 출처 정책이나 문서 분류가 요구되면 적용한 조항과 버전, 실제 입력, 결정, 미해결 건수를 함께 남긴다.
- 정보가 부족하면 부족한 항목과 수동 검토 필요성을 표시한다. 근거 없이 둘 중 하나로 강제 분류하지 않는다.
- 가중 계산 전에는 관측 단위, 모집단, 분모와 집단 구분이 무엇인지 확인한다. 정의가 다르면 수치를 먼저 합치지 않는다.
- LLM 기능의 확인이 필요하고 사용이 허용된 경우에만 실제 기능을 작게 검증한다. 고정된 소수의 질문과 기대 기준에 답할 수 없는 사례 및 모호한 사례를 포함한다.
- 입력, 실행 조건, 판정 기준과 결과를 다시 확인할 수 있게 남긴다. 실제로 실행하지 않았다면 `NOT RUN`으로 표시한다.

자동화의 시간 절감이나 비용 효과를 실제로 산정해야 한다면, 기존 수작업 시간과 새 흐름의 실행·사람 검토·예외 처리·유지 운영 시간을 같은 기준으로 비교한다. 개발·검증의 일회성 비용과 반복 비용을 구분하고 실측과 가정을 표시한다. 확인하지 않은 절감 효과를 구현 성과로 쓰지 않는다.

## 실험 결과를 실행·전달 후보로 바꿀 때

[기준본과 전달본 연결](baseline-and-delivery.md)에 따라 실제로 전달할 소스에서 시작해 빌드/실행·데이터/설정·결과·출력이 같은 후보인지 확인한다. 이미 떠 있는 이전 실행이나 저장소 해시만으로 최신 소스의 재현을 입증하지 않는다. 실제로 필요한 변경·재계산·오류 후 보존·재시작·조회·내보내기 흐름을 관련 범위에서 연결하고, 실행하지 못한 부분은 미검증으로 남긴다.

## 전달 전 검토

- 전체 해결 결과를 요구사항에 맞춰 검토하고, 실행한 검사와 남은 제한을 명확히 적는다.
- 코드가 바뀌었다면 이전에 확정한 보고서와 QA 결과가 아직 유효한지 확인한다. 변경 전 기록을 최신 결과처럼 제시하지 않는다.
- 요청된 정확한 경로에 결과를 저장하고 실제 전달 파일 목록을 확인한다.
- 숨김 폴더나 Git 무시 설정만으로 전달 대상에서 자동 제외됐다고 판단하지 않는다. 실제 플랫폼의 묶음 규칙을 확인하고 그 결과대로 설명한다.
- 보조 파일은 역할과 의존 관계를 확인한 뒤 처리한다. 전달 목록을 단순하게 보이게 하려고 무작정 삭제하지 않는다.
- 전체 해결을 마치고 해설·문답을 정리하는 단계에서는 별도의 문답을 약 여섯 개로 제안할 수 있다. 사용자가 원하면 하나씩 다루되, 단순 조사·부분 검토마다 반복하거나 추가 면담·이해 확인 절차를 강요하지 않는다.
- AI 지원이 금지된 범위에는 후속 도움을 제안하지 않는다. 허용된 결과 설명과 필요한 인계에서 마무리한다.
- 추론 수준 변경은 실제 필요가 있을 때만 마지막에 짧게 권한다. 변경은 사용자가 직접 하며 자동으로 바꾸지 않는다.
