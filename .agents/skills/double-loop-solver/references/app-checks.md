# 웹 동작을 작게 확인하기

기존에 합의한 작업 단위와 확인 범위를 유지한다. 이번 변경의 실제 사용 동작, 예상 응답, 다음 상태를 먼저 적고 필요한 만큼만 확인한다. 사용자가 일시정지를 요청하면 그 지점에서 멈춘다. 검사를 일정 개수로 맞추거나 새 도구를 설치할 필요는 없다.

**화면을 열 환경에 맞춰 구현한다.** 내장 미리보기나 제한된 창에서는 안내·오류·실행 확인을 페이지 안에서 처리하는 방식을 우선한다. 브라우저 기본 대화상자(`alert`·`confirm`·`prompt`), 새 창·탭, 자동 다운로드·인쇄·전체화면 전환에 필수 동작을 의존시키기 전에 실제 허용 여부와 지원을 확인한다. 확인 UI를 바꿔도 대상·영향·취소 선택이 분명해야 하며, 위험한 동작이 첫 클릭으로 바로 실행되게 하지 않는다. 요구된 파일 내보내기를 화면 텍스트로 대체하거나 없애지 말고 허용된 저장·전달 경로와 실제 파일을 검증한다. 다른 환경에서의 성공을 현재 미리보기의 성공으로 간주하지 않으며, 사람만 확인할 수 있는 부분은 아래 확인표에 남긴다.

**API가 있다면 실제 계약과 비교한다.** 허용된 로컬 개발 서버에서 응답의 상태코드·Content-Type·본문·변경 후 상태를 함께 본다. 정상 응답뿐 아니라 이번 변경과 관련된 빈 결과, 잘못된 입력, 없는 항목, 중복 요청을 골라 예상과 비교한다. 빈 목록과 서버 오류, JSON 오류와 HTML 오류 페이지를 같은 것으로 취급하지 않는다. 생성·목록·삭제 기능이 실제로 있으면 테스트용 항목을 생성하고 목록에서 확인한 뒤 삭제하고 다시 조회하는 흐름을 확인한다. 없는 기능을 가정하거나 운영 데이터를 바꾸지 않는다.

비동기 검색·필터가 실제로 있으면 이전 요청이 늦게 끝나도 최신 요청의 결과를 덮지 않는지 확인한다. 중복 제출 방지가 요구되는 상태 변경은 중복 요청 이후 상태도 검사한다. 소스 검토만으로 화면 동작까지 확인했다고 기록하지 않는다.

폼 입력, 재계산·저장 같은 상태 변경, 오래 걸리는 요청이 있으면 [웹 상태 예외 검증](web-state-checks.md)에서 관련 사례를 골라 정책·서버 상태·화면·저장 결과를 확인한다.

**인증이 있는 서비스는 실제 허용된 미리보기 주소에서도 확인한다.** 사용자가 접근하는 주소·경로에서 로그인 후 이동, 새로고침 뒤 세션 유지, 권한에 맞는 저장·조회와 로그아웃을 필요한 범위에서 사람이 확인한다. 로컬 주소의 HTTP 성공만으로 다른 호스트·경로를 거치는 화면까지 통과했다고 하지 않는다. 실패하면 관측된 응답·이동 경로·쿠키와 현재 환경 설정을 대조하며, 쿠키 차단을 원인으로 단정하거나 인증을 없애서 통과시키지 않는다. 이 확인을 위해 없는 로그인 기능을 추가하지 않는다.

저장 유지 요구는 새로고침, 앱 프로세스 재시작, 작업 환경 교체 중 어느 범위인지 구분한다. 파일 저장만으로 환경 교체 후 보존을 보장하지 않는다. 허용된 격리 환경에서 필요한 범위만 확인하고, 환경을 실제로 교체하지 못했다면 그 범위는 미검증으로 남긴다. 원본 작업 환경을 삭제해서 시험하지 않는다.

**계산 품질과 실제 사용 시간을 함께 본다.** 계산이 핵심인 서비스는 작은 예시의 함수 실행과 실제 제공 입력 규모의 서비스 실행을 구분한다. 실행 중인 요청 경로가 채택한 계산을 호출하는지 확인하고, 같은 입력·설정·기준에서 기준본과 품질·필수 조건·처리 범위·시간을 비교한다. 요청부터 결과 조회·필요한 저장/출력까지 걸린 시간을 확인하고, 가능하면 읽기·계산·검증·저장 시간을 나누어 병목을 찾는다. 실제 데이터의 희소 집단·극단값·경계 사례에서 누락과 품질 저하도 살핀다. 드문 정상 대상을 오류나 이상치로 간주해 조용히 제외하지 않는다. 별도 합성·확대 입력은 허용되고 규모 변화가 요구에 관련될 때만 사용하며 실측과 가정, 전체와 일부 입력, 실험 전용과 서비스 결과를 구분한다. 실제 작업 예산 안에서 검사하고, 운영 환경에 부하를 주거나 임의의 응답시간 합격선을 만들지 않는다. 화면의 진행 표시·오류 안내를 확인한 근거와 서버 시간 측정도 별도로 남긴다.

설치된 curl로 응답을 남길 수 있다. 아래 `run-new`는 예시 이름이며, 먼저 **기존에 없는 새 출력 폴더**를 만들고 사용한다. curl 출력 옵션은 기존 파일을 덮어쓸 수 있으므로 이전 결과의 경로를 재사용하지 않는다. Windows에서는 `curl.exe`, 다른 환경에서는 설치된 `curl`을 사용한다.

```powershell
curl.exe --max-time 5 --dump-header run-new/headers.txt --output run-new/body.txt --write-out "status=%{response_code} type=%{content_type}\n" http://127.0.0.1:8000/api/items
```

주소는 실제 허용된 개발 서버와 경로로 바꾼다. curl 종료코드 0만으로 HTTP 성공을 판단하지 않는다. 기본 curl은 4xx·5xx도 전송 자체가 성공하면 0으로 끝날 수 있다. `--fail-with-body`를 선택하면 오류 본문을 보존하면서 해당 응답에 종료코드 22를 주지만, 계약상 예상한 4xx는 기대된 결과일 수 있다. 시간 초과·연결 실패와 예상된 오류 응답을 구분해서 기록한다.

**화면은 사람이 허용된 미리보기에서 확인한다.** 키보드만으로 주요 입력·실행·오류 복구까지 이어지는지, 포커스 표시와 입력 라벨·오류 설명·빈 상태가 이해되는지, 대화상자를 닫은 뒤 조작 위치로 돌아오는지 본다. placeholder만 있는 입력과 이름 없는 아이콘 버튼, 색에만 의존한 상태 표시, 좁은 화면·긴 값에서 가려진 정보와 버튼을 점검한다. 표 내부의 필요한 가로 스크롤과 페이지 전체의 불필요한 넘침은 구분한다. 소스에서는 비어 있거나 중복된 `id`, `label[for]`와 해당 컨트롤의 `id` 연결, `aria-labelledby`·`aria-describedby`의 각 ID 참조를 확인한다. 자동 브라우저 조작 없이, 실제 화면에서 확인한 부분과 소스·HTTP로만 확인한 부분을 구분하며 전체 접근성이나 미실행한 보조기술 검사 통과로 확대하지 않는다.

**운영자가 결과를 판단할 수 있는지 본다.** 계산·설정 변경 화면이라면 현재 설정, 실행 중인 입력·설정·정책 스냅샷, 실제 적용 결과의 버전을 구분할 수 있어야 한다. 미처리 대상과 이유, 실패 뒤 다음 행동, 보존된 이전 결과의 상태를 확인한다. 사용자가 처음 읽을 지표와 필요한 이전 결과 비교가 업무 결정에 도움이 되는지도 살핀다. 내부 ID를 그대로 노출할 필요는 없으며 이해할 수 있는 시점·설정 요약 등으로 대응 관계를 표시할 수 있다. 이 확인 때문에 요청하지 않은 대시보드·인증·관리 기능을 추가하지 않는다.

## 사람이 확인할 최종 동선

화면이 있는 결과물은 최종 후보의 자체 검증 뒤, 전달 전에 사용자가 따라 할 확인표를 기존 해설의 검증 절에 모아 제시한다. 실제 필수 사용자 동작을 요구와 연결하고 빠진 동작은 미확인으로 드러낸다. 같은 동선이 여러 요구를 확인하면 함께 연결하고, 화면 밖에서만 검증할 수 있는 요구는 자동/API 근거와 한계로 구분한다. 별도 문서나 과제에 없는 기능을 추가하지 않는다.

| 요구·확인 항목 | 준비와 조작 | 실행 전 기대 결과·근거 | 실제 관찰·판정 |
| --- | --- | --- | --- |
| 실제 요구 위치/ID와 확인할 동작 | 후보·입력/설정 버전, 필요한 역할·시작 상태, 실제 URL, 입력값과 누를 순서 | 요구·확정 기준·독립 계산에서 얻은 값이나 상태 변화 | 사용자 보고와 근거; 통과 / 실패 / 미실행 / 환경상 확인 불가 / 변경 후 재확인 필요 |

절차와 기대 결과를 먼저 제공하고 사용자는 항목별 결과를 묶어 답할 수 있게 한다. 매 클릭마다 새 승인을 요구하지 않는다. 사용자 보고가 없으면 화면 관찰은 미실행이며 AI의 자동 검사 통과와 구분한다. 실패는 합의 범위에서 재현·수정하고 영향받는 항목만 다시 확인한다. 같은 후보·조건에서 이미 확인한 근거는 재사용하되, 후속 변경의 영향을 받은 행은 재확인 필요로 표시한다. 기대 결과의 오류나 기준 변경도 원래 관찰을 지우지 않고 근거와 변경 이유를 남긴다.

이 표는 확인 요청을 묶기 위한 것이며, [첫 E2E의 학습 초안](guided-collaboration.md#start-study-at-the-first-working-e2e)이나 진행을 막는 필수 미리보기 확인을 마지막까지 미루는 규칙이 아니다. 필요한 중간 확인은 그때 요청하고 이후 같은 표에 합친다. 답변 대기 중 독립된 승인 작업은 계속하며, 실제 남은 시간 안에서 중요한 미확인 동선을 우선한다. 사용자가 확인하지 않았다고 성공을 기록하거나, 이를 이유로 실제 마감을 넘기지 않는다. 확인표가 업무 정책 승인이나 개선 계속/종료 결정을 대신하지 않는다.

공식 근거: [curl 응답·출력·시간 제한 옵션](https://curl.se/docs/manpage.html), [W3C: 라벨과 컨트롤 연결](https://www.w3.org/WAI/WCAG22/Techniques/html/H44), [WAI-ARIA 1.2: ID 참조와 오류 처리](https://www.w3.org/TR/wai-aria-1.2/).
