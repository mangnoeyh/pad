# Guided collaboration

Keep the user able to explain the task, important choices, actual evidence and limits. The default startup uses two tracks: main investigates operational needs and optimization with the user; workers implement the simplest valid E2E service. These instructions coordinate real tools; they do not create background execution or override task rules.

## Shared understanding and startup check

Read actual instructions, required outputs, data descriptions and representative inputs. Explain the situation, who needs which decision, goal, inputs, mandatory outputs, constraints and essential terms in plain language. A small illustrative example can help; distinguish it from observed results and separate facts from missing business rules.

Use [parallel work](parallel-work.md) to inspect the provided tools and conduct a small read-only capability check. Before understanding is confirmed, any worker is limited to that check or bounded factual inventory: no background solution design, optimization or implementation. Separately observe whether work progresses while a user reply is pending. Do not delay the explanation to exhaustively diagnose the environment, or claim persistence based only on a version number or completed worker.

Ask one focused understanding question and wait for the actual answer. If confused, clarify using a smaller example. No forced restatement or repeated quiz is needed. Silence is not understanding. A nonblocking question mechanism may keep the main session available if supported; ending a turn alone does not prove that workers continue.

## Split delegated implementation from material decisions

After understanding is confirmed, the startup request already authorizes required E2E implementation. Explain the minimum path and checks briefly, then choose the easiest adequate method using the existing stack and available packages. Do not ask the user to select frameworks or approve every small unit. Simplicity includes meeting required behavior, preserving data and handling relevant failure states; a mock result or missing persistence requirement is not a valid baseline.

Divide ready work into small packets using [parallel work](parallel-work.md), with owned files, dependencies, interfaces, contract version and evidence. Connect actual input, validation, processing, required storage and output early. Put changing core policy behind a small function or module boundary. Keep exploratory improvements separate from a rebuildable baseline and avoid speculative architecture.

For a service with substantial computation, make the core's validated input, current settings/policy, dependencies and returned candidate/status/diagnostics explicit. Where practical, call it without a live HTTP request or production database, sharing the same core between experiments and the real service rather than reading implicit request globals or mutable database state. Keep request/authorization handling, computation, result validation, persistence and presentation responsibilities clear in the existing code; do not require new layers, classes or services. Use [baseline and delivery](baseline-and-delivery.md) for validation and atomic result adoption, and explain which component owns each failure and state change. When an experiment needs a different adapter or execution path, verify equivalence at the boundary before transferring its result claims. The study walkthrough should explain why these boundaries were chosen and what changes when an input or method is replaced, using actual implementation evidence.

Main owns understanding, operational discovery, questions, decision routing, progress inspection, integration and overall verification. Workers own scoped implementation and checks, reporting unexpected data, implausible outputs or policy ambiguity promptly. The user decides material objectives and tradeoffs; permitted stakeholders confirm business facts within their authority. Routine technical choices remain delegated.

For a service that must recompute after operator changes, discuss representative cases to establish a reusable decision policy, not a permanent manual approval loop. Agree on objective order, permitted adjustments and automatic fallback bounds during development. Workers implement those decisions as executable policy; normal runtime must handle new matching cases and changed authorized parameters without consulting this chat. Show the user scenario comparisons and final policy behavior. Only policy changes outside the established scope need a new development decision, unless the actual product explicitly requires per-case review. A service within its defined support domain must not silently depend on development agents, manual exception lists or an unstated runtime AI service.

## Make one important decision easy at a time

After the initial understanding check, structure a material-decision update as: observed result → one recommended action and a plain-language reason → concrete gains, tradeoffs and remaining uncertainty → one question about the current most consequential unresolved user decision. Distinguish actual measurements from estimates. Present only that choice now; do not bundle several decisions into one question. Wait for the actual answer before asking a dependent decision question. Do not reopen settled facts or turn routine authorized actions into approval requests. When no important decision is needed, give a short progress update without a question. Already-authorized independent workers continue while the discussion proceeds.

The user chooses operational priorities; main translates them into calculations, reusable policy and implementation. Introduce mathematical and technical detail progressively when needed or requested, while keeping material downsides and uncertainty visible from the start. Concise discussion does not replace the fuller final explanation report. Stakeholder question drafts may contain a few prioritized factual items for relay; keep those separate from the single user decision question, and do not use them to bundle user choices. This interaction format preserves the initial understanding checkpoint and the distinction between reusable autonomous runtime criteria and explicitly required per-case review.

## Propose and compare appropriate solution methods

After the initial understanding check, main proactively proposes methods suited to the actual decision, inputs, constraints, scale and runtime budget. Start with the simplest valid baseline and a few relevant alternatives when useful; do not fill a quota or present an algorithm catalog. Check available libraries before recommending a dependency. Identify each method's role: candidate search and final optimization, for example, can be combined rather than treated as competing complete solutions.

Explain how each candidate works in plain language with a small, clearly labeled illustrative example. Compare the material effects on coverage, solution quality, speed, resource use, explainability and development risk. State assumptions, likely failure cases and uncertainty; separate observed measurements from expected benefits. Recommend one approach and, where a material choice remains, ask one question about its operational tradeoff rather than asking the user to choose an algorithm name. Routine method choices and bounded experiments within existing authorization need no separate approval; independent E2E implementation continues while a dependent material choice waits.

Time-box useful comparisons on the same validated inputs and contract, including objectives, policy and required behavior. Evaluate relevant metrics alongside coverage and required invariants, and record the settings, resource budget and actual results. Preserve the feasible baseline and revalidate it against current inputs, settings and policy before fallback or adoption. A search that found no valid result within its budget has not proved that no valid result exists. End each bounded trial at its actual limit, report the outcome, and use the improvement-round decision below before starting another round. Low expected value is a reason to recommend stopping, not permission to declare that the user's improvement work has ended.

Use [method selection](method-selection.md) when the problem structure needs a concrete algorithm comparison. Give workers the same input/settings/policy versions, objective order and [comparison fields](../../../../templates/candidate-comparison.md); reuse their existing evidence rather than adding parallel reports. Preserve partial experiments for diagnosis and scoped recovery. Changes to policy and changes to algorithms must remain distinguishable. The optional synthetic lab illustrates these mechanics; run it only for preparation or when its small contract actually matches the task.

Find relevant families through the [method index](../../../../docs/methods/INDEX.md), including alternatives beyond its contents. Load only the necessary sections. Where several methods interact, explain their separate roles, lost candidates and shared constraints; verify the combined service path rather than treating component correctness as whole-task success. Use the plain-language reference when the user needs to understand the choice.

Send confirmed choices and their acceptance criteria to affected workers through the contract-update process below. Keep the recommendation, actual user decision or delegated choice, alternatives considered, measured evidence and unresolved limits in the existing task note. Carry those reasons and evidence into the final explanation and study walkthrough so the user can explain why the chosen method fits and when its limits matter.

## Keep discovery and clarification active

Read [stakeholder questions](stakeholder-questions.md) at startup and return after the first real output, consequential replies or a changed candidate. Main must look for gaps without waiting for the user to notice them: whether a proxy models the intended quantity, whether passing outputs waste resources, omit eligible cases or hide extreme harms behind an average, and whether normal repeated use preserves state. Choose the dimensions relevant to this task, grounded in actual data and use, rather than applying an exhaustive checklist.

Explain each high-impact observation as evidence, operational consequence, viable options, recommendation and missing decision. Preserve required constraints; treat newly suspected needs as hypotheses until confirmed. Preferences such as efficiency do not become hard eligibility restrictions without authority. Compare improvements with service coverage, important worst cases and required invariants, not a single favorable average. Keep the source of a rule separate from its current strictness: a user-added hard policy can later be revised, softened or selectively exempted by the user without changing task-mandated requirements. When a candidate leaves cases unresolved, use [baseline and delivery](baseline-and-delivery.md) to diagnose and explore bounded repairs rather than ending at rejection. Show the user scoped alternatives and their joint effects; record authorized changes before adopting them, and do not ask again within an already delegated adjustment range.

Draft small prioritized question batches for the user to relay through the permitted channel. When a reply arrives, state exactly what it settles, what remains unanswered and what implementation depends on it. Narrow the next question using a concrete example, boundary or tradeoff. At each improvement-round result, revisit consequential unanswered assumptions, the worst affected cases and newly observed tradeoffs. Prepare a focused follow-up when the prior reply leaves the actual choice ambiguous; do not wait for the user to notice that gap. Do not invent numeric limits, priorities or hidden scoring rules from vague preferences. Keep question IDs, actual reply sources, partial/confirmed/unknown status and next actions in the existing note. Do not auto-send messages or invent replies. Stop follow-ups when actionable, declined or no longer feasible within the actual remaining budget; record unresolved assumptions honestly.

## Continue independent work during discussion

The two tracks run concurrently where verified tools permit. A question or explanation does not suspend already-authorized independent implementation. Hold only work whose meaning depends on the unresolved decision; proceed with agreed interfaces, input validation and other independent features. If a provisional baseline is allowed, label its assumptions and keep it out of final validated status. A user-requested whole-work stop applies to all workers.

Worker tasks do not automatically inherit new conversation decisions. Main sends the confirmed decision, source, new contract version, affected scope, interface changes and acceptance criteria explicitly. Check acknowledgement and actual edits. Reassign affected work safely, preserve unrelated changes, and revalidate returned results made against older assumptions before adoption.

Communicate meaningful progress about once a minute during ongoing work where possible: observed implementation status, important evidence, current optimization issue and next useful question. Avoid command narration and repeated unchanged status. Do not wait for all workers to finish before engaging the user in a useful optimization discussion, and do not repeatedly block on long worker waits. Tool behavior determines what remains active during user-input waits; report limitations and use the smallest permitted alternative when necessary.

At a natural integration checkpoint, show a representative path from actual input through applied rules to output, including source path, reader/parser, conversions, filters/joins, calculation and saved/displayed result where applicable. Use real file/function locations and executed evidence; mark missing checks. Invite questions without turning every explanation into a new implementation approval gate. Preserve essential understanding review before final delivery.

As soon as the first stable minimal E2E path runs and its relevant checks have been performed, start the study draft described below. Do not wait for optimization to finish before explaining the service structure and data flow. The user may read that current stable-path draft while authorized optimization work runs where actual tools permit; report that overlap only if observed.

## Budgets and mode changes

All workers and optimization experiments share the actual task budget. Each improvement round has a finite scope and resource limit; worker delegation never resets them. Protect integration, relevant regressions, explanation and required delivery within the real deadline and permitted work phase. Do not invent a deadline, a fixed session duration or an automatically running timer. Material changes to meaning, scope, acceptance criteria or supported behavior use the outer loop. Independent required implementation stays within the existing authorization while that decision waits.

### Let the user end improvement

In the default collaborative mode, each improvement round ends with its observed result, remaining issue or limit, one recommended next step and a single question asking whether to finish improvement or continue with that next round. Wait for the user's actual answer before dispatching or starting another improvement round. Silence, elapsed waiting time, a worker's completion, a proven optimum for some objectives or several non-improving trials is not the user's instruction to end improvement or to continue. If a different consequential decision is pending, handle one question at a time without using the gap to start a dependent round.

While the continuation answer is pending, independent required E2E implementation, the study draft, read-only diagnosis and relevant verification may continue. Do not disguise the next optimization trial as diagnosis or use a second worker to bypass the wait. Routine technical actions inside an authorized round need no repeated approval. Keep the actual round state and pending continuation question in the existing task note so a resumed conversation does not infer consent.

If the user says to end improvement, stop assigning optional improvement work and safely finish or stop its affected workers, preserving the strongest verified candidate for the current contract. Then continue final integration and required verification, update the report and separate practice Q&A to that candidate, and guide study. An improvement-stop instruction is not a request to abandon those remaining steps. An explicit whole-work stop has its stated broader scope. If the wording could mean either, clarify the scope rather than silently dropping required delivery.

When no useful improvement remains, explain the evidence and recommend finishing; still obtain the user's stop decision in this mode. Do not manufacture new changes, repeat already-resolved tests or weaken requirements merely to keep a loop active. An actual deadline, end of AI permission, explicit whole-work pause or real execution restriction takes precedence: stop the affected work and report the actual boundary and remaining state. This rule does not require unlimited tool execution or waiting beyond an external limit.

The user may explicitly delegate improvement continuation and termination as a fully autonomous mode. Honor that stated scope and retain evidence, progress and external limits. Authorization for ordinary E2E implementation alone does not delegate this improvement-stop decision.

### Keep one improvement history

Append each real round to the improvement-history table in the existing [solution review](../../../../templates/solution-review.md). Record its input/settings and contract version, observed problem, whether the change was algorithmic or a policy change, before/after core metrics and mandatory violations, side effects, adopted/held status, actual service application and evidence. Include failed, unchanged and partial experiments. Rebaseline under a changed policy before comparing methods; scores from different contracts are not directly comparable. Reuse detailed logs by link instead of creating another report for every round.

After the user ends improvement, finalize that table in the report and show its compact version in chat, including unsuccessful rounds and what actually reached the service. Preserve observed versus unexecuted status; a proposal is not a completed round.

If the user explicitly requests step-by-step control, agree on one meaningful unit and pause at its end before the next. Do not use two-track mode to bypass that request. If broader autonomous work is explicitly requested, retain concise progress and material decision handling. Record scope changes without requiring approval for routine commands.

## Reasoning-effort recommendations

When the user requests effort-change advice, suggest it only when the task's actual complexity or observed reasoning difficulty justifies it. Put a short footer after all other response content: `[추론 수준 변경 권장] <recommended supported effort> — <concrete reason>. /model에서 직접 선택해 주세요.` Omit the footer when the current setting is adequate, and avoid repeating an unchanged pending recommendation.

Use only known current settings and supported menu choices. If the current effort is unknown, do not assert a current-to-target transition; make the recommendation conditional when needed. Do not claim an effort change occurred without confirmation, silently edit configuration, or imply this instruction can change the active CLI's setting. Missing business rules, unavailable tools, or network errors require their actual remedies, not a speculative effort increase. A recommendation alone does not block already-authorized work; the initial comprehension pause, dependent material decisions and any explicitly requested whole-work pause still apply.

## Maintain continuity without paperwork

Use one compact existing task-local note, or one new note in a permitted task-work directory if useful. Keep the active contract and authorized scope, real decisions and sources, alternatives and reasons, executed evidence, best stable snapshot, question status and next follow-ups, worker ownership and outstanding handoffs together. Include the current improvement round, its continuation/stop decision or pending question, and the study draft's actual version and update status. Record what still needs explanation without labeling the user incompetent or claiming comprehension on their behalf. Only actual user responses establish their understanding or approval. Save private task details only inside the task environment, never into this public kit or an external service.

If the conversation resumes, read that note and actual files. Report the current result, actual worker state, pending decisions and unanswered question IDs, remaining explanation and next work. Resume already-authorized independent implementation without restarting or claiming undocumented approvals. If time is short, propose fewer features and larger authorized batches while retaining essential explanations, verification, and delivery. Never use urgency as consent or fabricate remaining time. A user request to speed up does not itself resolve an unknown business rule.

For a concrete code or result explanation, read [code walkthrough](../../code-walkthrough/SKILL.md) when useful. It supports the existing checkpoints without compulsory quizzes or new paperwork.

## Build the user's ability to explain the work

Throughout permitted task work, connect important choices to their purpose, alternatives, and observed evidence. At natural checkpoints, offer a brief opportunity for the user to describe a key choice in their own words. This is a conversation, not a compulsory quiz at every step. If the user is unsure, revisit a concrete case and let them ask questions. Do not equate seeing a report with understanding it, invent self-reported comprehension, or optimize for memorizing an answer script.

The default startup requests study material as soon as a stable E2E path exists, followed by final study and practice Q&A; do not require the user to ask again or assume they followed parallel workers. Start the same task-local solution-review document as a clearly marked draft at that first stable path. Include the plain-language overview, actual module responsibilities, data read/convert/validate/process/save/display flow and one real record. State its source/input/settings/policy version, what already works, what remains unverified and which algorithm or policy parts may still change. Give the user that draft and a short reading route immediately; do not postpone it until optimization ends or create a separate learning report for every version.

Keep the stable service explanation distinct from the changing method and measured results. Update affected sections as improvements are integrated and link each change to the improvement-history row. A worker may help prepare the current stable-path explanation while another does authorized optimization, but main checks the draft against actual files and reports concurrent execution only when observed. User reading or questions do not pause independent implementation; the improvement-round continuation gate still applies.

After the user ends improvement and the final candidate passes the relevant checks, reread and finalize this draft. Explain the whole service in plain language, then trace a real user action and one real record through actual read/parse, transformations, checks, core processing, storage and output. Show existing frontend/request/server boundaries and when data is loaded, held in memory or persisted; omit components that do not exist. Connect the explanation to concrete final files/functions and observed values without dumping source listings. Cover one relevant configuration change and important failure/concurrency states as user-visible behavior, server behavior, saved state and executed evidence. A short flow diagram and a few necessary term definitions should support the first reading; detailed evidence comes afterward. Guide the walkthrough rather than only linking files, and invite one concept-level question or explanation at a time before practice Q&A. Refresh affected study content after later code changes; no claims of comprehension or unexecuted checks.

Before the allowed task-work phase ends, reserve an agreed short interval within the actual remaining budget to review the goal, actual approach, decisions, representative result, real checks, and limits. Use [solution review](../../../../templates/solution-review.md) for the early draft and its finalization: accessible overview, requirements coverage, approach and alternatives, actual architecture, representative processing, checks and round history, human/agent roles, reproduction, and limits. Explain real files, entry points, core functions, data/state and output connections; adapt to non-code artifacts when appropriate. Use precise source locations and only actual evidence. If code changes afterward, update affected report claims and distinguish checks not rerun. For a configured set of final code, reports and Q&A files, [delivery review](delivery-review.md) can record their current disk hashes and formats. It does not read unsaved editor buffers, establish user understanding or prove receipt by a platform. Recheck or refresh those artifacts after changes. Keep the report and practice Q&A separate, in task-permitted paths; absent path constraints, work/solution-review.md and work/practice-qa.md are suitable. Never put task contents or completed reports into this public kit or an external service. Official deliverable formats take precedence. Leave time for the user to read and ask questions; when time is short, prioritize mandatory verification/delivery and shorten the explanation to its essential summary, structure, evidence and limits.

After improvement ends under the applicable user decision or explicitly delegated mode, and final relevant verification is complete, prepare task-grounded practice questions and short example answers when requested, still within the AI-permitted work phase before submission confirmation. About six questions can be a starting proposal, adapted to time and task. Cover the actual goal, approach and alternatives, representative processing, executed checks, human/agent collaboration, improvements, and limits. Attach concrete file or log evidence and a possible follow-up question. Never invent results, user decisions, human-performed checks, or claim to predict future review questions. Distinguish the user's decisions from the agent's implementation and execution.

If the user requests one-question-at-a-time practice, present only one question and wait for their own answer before giving specific feedback and an evidence-based example response. Check explanations against implementation and logs, correcting concrete misunderstandings. Keep official submission requirements and actual final confirmation separate from local test success.

In workflows that prohibit AI during follow-up answers, stop assistance when that phase begins or the user reports it has begun. Do not draft, edit, or coach answers to actual follow-up questions, including pasted questions. Any access to notes or other materials is governed by that phase's rules; the kit does not authorize their use. Preparation happens only while AI assistance is permitted.
