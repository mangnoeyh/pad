# Guided collaboration

Keep the user able to explain the problem, important choices, actual evidence and limits. This reference owns understanding, material-decision discussion and study. Follow the actual requested mode: the default START_HERE request selects an initial understanding pause, autonomous required E2E implementation, user-controlled improvement ending, early study and final explanation/Q&A. A direct skill invocation does not itself request every one of those outputs. Honor explicit stage-by-stage control or broader delegation instead.

## Shared understanding before solving

Read the actual instructions, outputs, data descriptions and representative inputs. Explain who needs which decision, the goal, inputs, required result, constraints and essential terms in plain language. Use a small labeled illustration where helpful; separate supplied facts from assumptions and missing business rules.

Choose quality checks from that required result: feasible and useful decisions for allocation, supported conclusions for analysis, consistent case handling for policy, understandable and applicable material for learning, and complete user actions for an interactive product. A task may combine these; do not force a single category, numerical score or optimization objective. Main discusses the consequential quality choices while workers produce the authorized artifact. Use the solver's verification table for the relevant checks.

In the default mode, ask one focused understanding question and wait for the actual answer before solution design or implementation. If needed, explain a smaller example. Do not require formal restatement or repeated quizzes, or count silence as understanding. Before that answer, workers may only perform bounded factual inventory or the brief read-only capability check in [parallel work](parallel-work.md). Do not delay explanation for exhaustive environment diagnosis. Parallel execution and progress during a user-reply wait are distinct claims; report only what actual tools establish.

## Required implementation and material decisions

Once understanding is confirmed, the default startup's required E2E implementation is authorized. Briefly explain the simplest adequate path and checks, then proceed in the existing stack without asking the user to select frameworks or reapprove routine units. Connect actual input → validation/processing → required storage → output early. Required integrity and relevant failure handling belong in that path; mocks or missing required persistence are not E2E completion.

For a non-code deliverable, the same E2E milestone means actual source material → analysis, decision or composition → the required usable output, with its essential content checks. A document does not require an app, API, database or model. Start the selected learning draft at that milestone as well; explain the real reasoning and source flow using the existing review template rather than inventing code stages.

Main owns operational discussion, progress, decisions, integration and overall verification. Workers implement and check ready scoped tasks. Use [parallel work](parallel-work.md) for capabilities, packets, file ownership, explicit decision updates and reconciliation of stale results; conversation changes are not automatically worker instructions. While a material choice waits, continue already-authorized work independent of it. Hold only dependent changes, label any permitted provisional baseline, and honor a whole-work stop across workers. Do not promise unobserved background progress or wait for every worker before discussing a useful result.

During active work, share meaningful progress about once a minute where possible: observed implementation status, important evidence and the next useful discussion. Avoid command narration, unchanged polling and long waits that prevent conversation.

For a configurable service, development dialogue establishes reusable policy; normal execution applies it to current inputs and authorized settings. Use [baseline and delivery](baseline-and-delivery.md) for core boundaries, automatic recovery/exception eligibility, validation and result adoption. Explain representative cases without making ordinary reruns depend on this chat, manual exception lists or unstated runtime AI. A new policy outside the agreed range needs a development decision; changing a permitted runtime value does not.

## One important decision at a time

Use this order: **observed result → one recommendation and reason → concrete gains, tradeoffs and uncertainty → one question about the most consequential unresolved user choice**. Give a small example or useful numbers; distinguish measurements, estimates and unknowns. Do not bundle several decisions, hide material disadvantages, reopen settled choices or ask questions for routine work. Wait for the actual answer before a dependent question. With no important decision, give a concise progress update and continue.

The user chooses priorities within their authority; main translates them into calculations, validation and implementation. Introduce formulas and technical detail only when needed or requested, keeping fuller evidence in the explanation. When a criterion belongs to a stakeholder, prepare a follow-up for that stakeholder's incomplete answer before asking the user to choose its meaning; an authorized user preference is a different decision. Use [stakeholder questions](stakeholder-questions.md) when first interpreting operational requirements and after meaningful results or partial replies: it owns perspective discovery, concrete follow-ups and business-fact/user-tradeoff/technical-experiment routing. Suspected needs are not authority to invent constraints or a hidden rubric.

## Discuss methods plainly

After understanding, proactively propose methods when they materially affect quality, coverage, runtime or resources. Ground the simplest valid baseline and a few useful alternatives in actual input, constraints, scale and available packages; do not wait for the user to name an algorithm or fill a candidate quota. Explain how each works with a small labeled example, its role, assumptions, failure cases, costs and material tradeoffs. Recommend one and ask only the unresolved operational choice, not which algorithm name the user likes. Routine comparisons inside the authorized round remain technical work.

Read [method selection](method-selection.md) for a concrete comparison and use the [method index](../../../../docs/methods/INDEX.md) only for relevant sections, including suitable alternatives outside the catalog. It covers comparable input/settings/policy and budgets, protected conditions, candidate pruning and combined stages. Give workers the agreed comparison and acceptance criteria; link their actual evidence instead of adding parallel reports. Carry recommendations, actual decisions, alternatives, measured results and limits into the final explanation. Synthetic examples are preparation, not evidence about the actual service.

## Start study at the first working E2E

As soon as actual input reaches required output/storage through the minimal path and its relevant essential checks run, start the same task-local [solution review](../../../../templates/solution-review.md) as a clearly marked draft. Do not wait for optimization or all final verification. In the default startup this is already requested: give its location, a short plain-language overview and a reading route immediately. Include actual structure, data flow and one real record, source/input/settings/policy version, what works, unverified parts and what may change. Stable service structure should be readable while methods and results evolve.

At that first E2E, operationally important tasks also trigger the [independent operational omission review](parallel-work.md#구현-설명과-독립된-작은-검토). It challenges actual requirements and results independently of implementation testing; use the parallel reference for assignment and resolution. Do not let functional tests or a favorable objective replace it.

Guide study from an easy overview to one real user action/record, then configuration and important failures, then code/evidence. Trace actual reading/parsing, conversions, validation, joins/filters, core calculation, storage and display/export where present. Explain when data is loaded, temporary in memory, reused or persisted. Link real files/functions and observed values; omit nonexistent APIs, databases or stages. Explain why responsibility boundaries were chosen and what an input/method change affects. For configurable services, follow one actual setting change into recomputation and automatic policy, separating human development choices from runtime behavior. For failures, connect user-visible behavior, processing, saved state and executed checks; HTTP/code inspection is not a human screen check.

Update affected parts of the same draft as changes are adopted, linked to its single cumulative improvement table. Main checks explanations, including its own, against the actual saved candidate used in the walkthrough. Identify that candidate and its actual inputs/settings; verify each stated record, assignment and intermediate value against its rows or other source evidence, then recompute any displayed subtotal. A matching total does not validate the named records or prove that an older example describes the adopted result. Keep historical examples labeled and check the corresponding Q&A against the same evidence. Continue independent work during reading/questions where tools permit, but do not bypass the [improvement-round lifecycle](improvement-rounds.md). It owns continue/end, budgets and the single current-state block; use that block on resume instead of reconstructing authority from stale notes.

## Final explanation and practice

After improvement ends under the selected mode and final relevant checks run, reread and finalize the draft against that candidate. Explain the whole result and guide the real-record walkthrough before practice Q&A; linking a file alone is insufficient. Preserve goal, approach and alternatives, requirements coverage, actual architecture/data flow, checks, improvement history, human/agent roles, reproduction and limits. Adapt to non-code artifacts. Later code or policy changes require affected explanation/Q&A updates and a clear statement of checks not rerun.

The default startup already requests a separate task-grounded Q&A file; do not ask the user to request it again. For other modes, prepare it when requested. About six questions can be a starting proposal, adapted to time and task, covering goal, method, representative processing, evidence, collaboration, improvements and limits, with short example answers, concrete evidence and possible follow-ups. These are preparation, not predictions of actual review questions. In one-at-a-time practice, ask one question, wait for the user's answer, then give specific feedback and an evidence-based example. Never invent human actions, decisions, comprehension or results.

At natural checkpoints invite a question or brief explanation in the user's own words. Correct concrete misunderstandings with actual examples; do not force repeated quizzes, label the user or confuse reading with understanding. Leave time inside the real remaining budget for learning and mandatory delivery. If short, prioritize verification/delivery and shorten explanation to its overview, real flow, essential evidence and limits. Keep report and Q&A in task-permitted paths (otherwise `work/solution-review.md` and `work/practice-qa.md`); private task content does not belong in the public kit. [Delivery review](delivery-review.md) can check configured disk artifacts, but cannot prove user understanding, unsaved editor state or platform receipt.

When an AI-prohibited follow-up phase begins, stop drafting, editing or coaching actual answers, including pasted questions. Preparation and access to notes follow that phase's rules.

## Optional effort advice

When requested and justified by actual reasoning difficulty, append `[추론 수준 변경 권장] <supported effort> — <concrete reason>. /model에서 직접 선택해 주세요.` Use only known supported choices; make an unknown current setting conditional. Do not repeatedly recommend an unchanged setting, claim it changed, modify configuration or stop authorized work for the advice. Tool failures and missing business facts need their actual remedies.
