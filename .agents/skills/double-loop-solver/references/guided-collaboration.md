# Guided collaboration

Keep the user able to explain the task, important choices, actual evidence and limits. The default startup uses two tracks: main investigates operational needs and optimization with the user; workers implement the simplest valid E2E service. These instructions coordinate real tools; they do not create background execution or override task rules.

## Shared understanding and startup check

Read actual instructions, required outputs, data descriptions and representative inputs. Explain the situation, who needs which decision, goal, inputs, mandatory outputs, constraints and essential terms in plain language. A small illustrative example can help; distinguish it from observed results and separate facts from missing business rules.

Use [parallel work](parallel-work.md) to inspect the provided tools and conduct a small read-only capability check. Before understanding is confirmed, any worker is limited to that check or bounded factual inventory: no background solution design, optimization or implementation. Separately observe whether work progresses while a user reply is pending. Do not delay the explanation to exhaustively diagnose the environment, or claim persistence based only on a version number or completed worker.

Ask one focused understanding question and wait for the actual answer. If confused, clarify using a smaller example. No forced restatement or repeated quiz is needed. Silence is not understanding. A nonblocking question mechanism may keep the main session available if supported; ending a turn alone does not prove that workers continue.

## Split delegated implementation from material decisions

After understanding is confirmed, the startup request already authorizes required E2E implementation. Explain the minimum path and checks briefly, then choose the easiest adequate method using the existing stack and available packages. Do not ask the user to select frameworks or approve every small unit. Simplicity includes meeting required behavior, preserving data and handling relevant failure states; a mock result or missing persistence requirement is not a valid baseline.

Divide ready work into small packets using [parallel work](parallel-work.md), with owned files, dependencies, interfaces, contract version and evidence. Connect actual input, validation, processing, required storage and output early. Put changing core policy behind a small function or module boundary. Keep exploratory improvements separate from a rebuildable baseline and avoid speculative architecture.

Main owns understanding, operational discovery, questions, decision routing, progress inspection, integration and overall verification. Workers own scoped implementation and checks, reporting unexpected data, implausible outputs or policy ambiguity promptly. The user decides material objectives and tradeoffs; permitted stakeholders confirm business facts within their authority. Routine technical choices remain delegated.

For a service that must recompute after operator changes, discuss representative cases to establish a reusable decision policy, not a permanent manual approval loop. Agree on objective order, permitted adjustments and automatic fallback bounds during development. Workers implement those decisions as executable policy; normal runtime must handle new matching cases and changed authorized parameters without consulting this chat. Show the user scenario comparisons and final policy behavior. Only policy changes outside the established scope need a new development decision, unless the actual product explicitly requires per-case review. A service within its defined support domain must not silently depend on development agents, manual exception lists or an unstated runtime AI service.

## Make one important decision easy at a time

After the initial understanding check, structure a material-decision update as: observed result → one recommended action and a plain-language reason → concrete gains, tradeoffs and remaining uncertainty → one question about the current most consequential unresolved user decision. Distinguish actual measurements from estimates. Present only that choice now; do not bundle several decisions into one question. Wait for the actual answer before asking a dependent decision question. Do not reopen settled facts or turn routine authorized actions into approval requests. When no important decision is needed, give a short progress update without a question. Already-authorized independent workers continue while the discussion proceeds.

The user chooses operational priorities; main translates them into calculations, reusable policy and implementation. Introduce mathematical and technical detail progressively when needed or requested, while keeping material downsides and uncertainty visible from the start. Concise discussion does not replace the fuller final explanation report. Stakeholder question drafts may contain a few prioritized factual items for relay; keep those separate from the single user decision question, and do not use them to bundle user choices. This interaction format preserves the initial understanding checkpoint and the distinction between reusable autonomous runtime criteria and explicitly required per-case review.

## Keep discovery and clarification active

Read [stakeholder questions](stakeholder-questions.md) at startup and return after the first real output, consequential replies or a changed candidate. Main must look for gaps without waiting for the user to notice them: whether a proxy models the intended quantity, whether passing outputs waste resources, omit eligible cases or hide extreme harms behind an average, and whether normal repeated use preserves state. Choose the dimensions relevant to this task, grounded in actual data and use, rather than applying an exhaustive checklist.

Explain each high-impact observation as evidence, operational consequence, viable options, recommendation and missing decision. Preserve required constraints; treat newly suspected needs as hypotheses until confirmed. Preferences such as efficiency do not become hard eligibility restrictions without authority. Compare improvements with service coverage, important worst cases and required invariants, not a single favorable average. Keep the source of a rule separate from its current strictness: a user-added hard policy can later be revised, softened or selectively exempted by the user without changing task-mandated requirements. When a candidate leaves cases unresolved, use [baseline and delivery](baseline-and-delivery.md) to diagnose and explore bounded repairs rather than ending at rejection. Show the user scoped alternatives and their joint effects; record authorized changes before adopting them, and do not ask again within an already delegated adjustment range.

Draft small prioritized question batches for the user to relay through the permitted channel. When a reply arrives, state exactly what it settles, what remains unanswered and what implementation depends on it. Narrow the next question using a concrete example, boundary or tradeoff. Keep question IDs, actual reply sources, partial/confirmed/unknown status and next actions in the existing note. Do not auto-send messages or invent replies. Stop follow-ups when actionable, declined or no longer feasible within the remaining budget; record unresolved assumptions honestly.

## Continue independent work during discussion

The two tracks run concurrently where verified tools permit. A question or explanation does not suspend already-authorized independent implementation. Hold only work whose meaning depends on the unresolved decision; proceed with agreed interfaces, input validation and other independent features. If a provisional baseline is allowed, label its assumptions and keep it out of final validated status. A user-requested whole-work stop applies to all workers.

Worker tasks do not automatically inherit new conversation decisions. Main sends the confirmed decision, source, new contract version, affected scope, interface changes and acceptance criteria explicitly. Check acknowledgement and actual edits. Reassign affected work safely, preserve unrelated changes, and revalidate returned results made against older assumptions before adoption.

Communicate meaningful progress about once a minute during ongoing work where possible: observed implementation status, important evidence, current optimization issue and next useful question. Avoid command narration and repeated unchanged status. Do not wait for all workers to finish before engaging the user in a useful optimization discussion, and do not repeatedly block on long worker waits. Tool behavior determines what remains active during user-input waits; report limitations and use the smallest permitted alternative when necessary.

At a natural integration checkpoint, show a representative path from actual input through applied rules to output, including source path, reader/parser, conversions, filters/joins, calculation and saved/displayed result where applicable. Use real file/function locations and executed evidence; mark missing checks. Invite questions without turning every explanation into a new implementation approval gate. Preserve essential understanding review before final delivery.

## Budgets and mode changes

All workers and optimization experiments share the actual task budget. Use finite iterations and stop low-value improvement early; protect integration, relevant regressions, explanation and required delivery. Material changes to meaning, scope, acceptance criteria or supported behavior use the outer loop. Independent implementation stays within the existing authorization while that decision waits.

If the user explicitly requests step-by-step control, agree on one meaningful unit and pause at its end before the next. Do not use two-track mode to bypass that request. If broader autonomous work is explicitly requested, retain concise progress and material decision handling. Record scope changes without requiring approval for routine commands.

## Reasoning-effort recommendations

When the user requests effort-change advice, suggest it only when the task's actual complexity or observed reasoning difficulty justifies it. Put a short footer after all other response content: `[추론 수준 변경 권장] <recommended supported effort> — <concrete reason>. /model에서 직접 선택해 주세요.` Omit the footer when the current setting is adequate, and avoid repeating an unchanged pending recommendation.

Use only known current settings and supported menu choices. If the current effort is unknown, do not assert a current-to-target transition; make the recommendation conditional when needed. Do not claim an effort change occurred without confirmation, silently edit configuration, or imply this instruction can change the active CLI's setting. Missing business rules, unavailable tools, or network errors require their actual remedies, not a speculative effort increase. A recommendation alone does not block already-authorized work; the initial comprehension pause, dependent material decisions and any explicitly requested whole-work pause still apply.

## Maintain continuity without paperwork

Use one compact existing task-local note, or one new note in a permitted task-work directory if useful. Keep the active contract and authorized scope, real decisions and sources, alternatives and reasons, executed evidence, best stable snapshot, question status and next follow-ups, worker ownership and outstanding handoffs together. Record what still needs explanation without labeling the user incompetent or claiming comprehension on their behalf. Only actual user responses establish their understanding or approval. Save private task details only inside the task environment, never into this public kit or an external service.

If the conversation resumes, read that note and actual files. Report the current result, actual worker state, pending decisions and unanswered question IDs, remaining explanation and next work. Resume already-authorized independent implementation without restarting or claiming undocumented approvals. If time is short, propose fewer features and larger authorized batches while retaining essential explanations, verification, and delivery. Never use urgency as consent or fabricate remaining time. A user request to speed up does not itself resolve an unknown business rule.

For a concrete code or result explanation, read [code walkthrough](../../code-walkthrough/SKILL.md) when useful. It supports the existing checkpoints without compulsory quizzes or new paperwork.

## Build the user's ability to explain the work

Throughout permitted task work, connect important choices to their purpose, alternatives, and observed evidence. At natural checkpoints, offer a brief opportunity for the user to describe a key choice in their own words. This is a conversation, not a compulsory quiz at every step. If the user is unsure, revisit a concrete case and let them ask questions. Do not equate seeing a report with understanding it, invent self-reported comprehension, or optimize for memorizing an answer script.

Before the allowed task-work phase ends, reserve an agreed short interval within the actual remaining budget to review the goal, actual approach, decisions, representative result, real checks, and limits. When a full explanation report is requested, reread the final implementation, outputs, decisions, and executed evidence after implementation and verification. Use [solution review](../../../../templates/solution-review.md) to write an accessible overview followed by requirements coverage, approach and alternatives, actual architecture, representative processing, checks and improvements, human/agent roles, reproduction, and limits. Explain real files, entry points, core functions, data/state and output connections; adapt to non-code artifacts when appropriate. Use precise source locations and only actual evidence. If code changes afterward, update affected report claims and distinguish checks not rerun. For a configured set of final code, reports and Q&A files, [delivery review](delivery-review.md) can record their current disk hashes and formats. It does not read unsaved editor buffers, establish user understanding or prove receipt by a platform. Recheck or refresh those artifacts after changes. Keep the report and practice Q&A separate, in task-permitted paths; absent path constraints, work/solution-review.md and work/practice-qa.md are suitable. Never put task contents or completed reports into this public kit or an external service. Official deliverable formats take precedence. Leave time for the user to read and ask questions; when time is short, prioritize mandatory verification/delivery and shorten the explanation to its essential summary, structure, evidence and limits.

Once implementation and verification are complete, prepare task-grounded practice questions and short example answers when requested, still within the AI-permitted work phase before submission confirmation. About six questions can be a starting proposal, adapted to time and task. Cover the actual goal, approach and alternatives, representative processing, executed checks, human/agent collaboration, improvements, and limits. Attach concrete file or log evidence and a possible follow-up question. Never invent results, user decisions, human-performed checks, or claim to predict future review questions. Distinguish the user's decisions from the agent's implementation and execution.

If the user requests one-question-at-a-time practice, present only one question and wait for their own answer before giving specific feedback and an evidence-based example response. Check explanations against implementation and logs, correcting concrete misunderstandings. Keep official submission requirements and actual final confirmation separate from local test success.

In workflows that prohibit AI during follow-up answers, stop assistance when that phase begins or the user reports it has begun. Do not draft, edit, or coach answers to actual follow-up questions, including pasted questions. Any access to notes or other materials is governed by that phase's rules; the kit does not authorize their use. Preparation happens only while AI assistance is permitted.
