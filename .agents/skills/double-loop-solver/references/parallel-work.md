# 메인과 작업자의 병렬 운영

제공된 환경의 실제 위임 기능을 사용한다. 기본 운영은 **메인이 사용자와 문제의 의미·운영 목표·핵심 최적화를 논의하고, 작업자들은 확정된 범위의 가장 간단한 E2E 구현을 진행하는 방식**이다. 병렬화 자체보다 빨리 연결되는 결과와 검증 가능한 개선이 우선이다.

## 시작할 때 확인할 기능

처음에는 실제 도구 목록과 지원 인자를 확인하고, 문제 이해를 위한 읽기만 한다. 사용자의 최초 이해 확인 전에는 설계·구현이나 백그라운드 풀이를 시작하지 않는다. 버전이나 모델 목록만으로 병렬 실행 또는 작업자 생존을 확정하지 않는다.

초기에는 작은 독립 읽기 과제로 실행·상태 확인·후속 전달을 점검한다. 이해 확인 후 실제 구현과 첫 논의에서 사용자 답변 대기 중 진행을 추가로 관찰한다. 이미 확인한 기능을 다시 검사하지 않는다. 별도의 오래 걸리는 실험, 인위적인 대기, 전체 구현을 끝내고 나서 하는 검사는 필요 없다.

- **실행:** 작업자가 실제 생성되고, 메인이 다른 일을 하는 동안 각 과제의 진행·완료 증거를 받을 수 있는가?
- **조정:** 실행 중인 작업자에게 후속 지시를 보내고 상태·결과를 확인할 수 있는가? 실제 작업자 ID와 담당 범위를 기록한다.
- **사용자 답변 대기:** 첫 실제 논의에서 사용자 질문이 열린 동안에도 작업자 진행 기록이 생기는가? 지원되는 비동기 질문·상태 확인을 사용하고, 답변 전후에 관찰한 시각·결과를 근거로 삼는다. 사용자를 기다리는 상황이 아직 없었다면 미확인으로 둔다.

동시 실행과 메인의 최종 응답 뒤 계속 실행되는 것은 별개다. 메인이 모든 결과를 기다린 뒤 질문한 사례는 대화 중 지속 실행의 증거가 아니다. 확인 전에는 “답을 기다리는 동안에도 계속 구현 중”이라고 보장하지 않는다. 상태를 확인하지 못했다면 마지막 관측 상태와 확인되지 않은 범위만 알린다. 실제 위임 도구가 없으면 그 사실을 짧게 밝히고 가능한 범위로 진행한다. 우회용 실행기나 복잡한 대체 체계를 만들지 않는다.

## 두 트랙의 경계

- **메인:** 사용자와 요구의 의미, 숨은 운영상 문제, 가정의 정확도, 개선 목표와 교환 관계를 논의한다. 필요한 담당자 질문은 [질문 지침](stakeholder-questions.md)에 따라 정리하고, 실제 답변에서 확정된 결정만 작업자에게 전달한다. 통합과 전체 결과 검증도 메인의 책임이다.
- **작업자:** 현재 확정된 요구와 승인된 범위에서 입력→처리→결과를 잇는 최소 E2E를 자율 구현한다. 여러 방법이 있으면 필수 요구를 만족하며 구현·실행·검증 비용이 가장 작은 방법을 선택한다. 일상적인 기술 선택마다 사용자의 결정을 요구하지 않는다.
- 처음 문제 이해를 확인한 뒤, 사용자가 위임한 E2E 전체 범위는 이미 실행 가능한 범위다. 메인의 설명이나 최적화 논의 때문에 그 안의 다음 작업 단위를 매번 재승인받지 않는다. 사용자가 더 좁은 범위나 명시적인 중단을 요청하면 따른다.
- 목적함수·업무 기준·현실의 근사·지원 범위를 바꾸는 선택은 메인으로 올린다. “쉽게 구현”은 필수 조건을 생략하거나 임시 가정을 확정 사실로 바꾸라는 뜻이 아니다. 미정 기준에 직접 의존하는 부분만 보류하고 독립적인 입력 검증·화면·저장·인터페이스 준비는 계속한다.
- 가능하면 기존 구조 안에서 핵심 계산을 교체할 경계를 정한다. 최적화 답변을 기다리느라 전체 서비스를 막거나, 교체 가능성을 이유로 새 프레임워크·플러그인 구조를 만들지 않는다. 임시 계산이나 모의 결과는 표시하며 최종 해결로 보고하지 않는다.

초기에 소수의 작업자로 시작해 실제 동시 실행 한도와 의존 관계에 맞춰 조절한다. 모든 기능을 완성한 뒤 처음 연결하지 말고, 작은 실제 입력으로 최소 E2E를 먼저 연결·검증한다. 그 결과의 분포·극단 사례·운영상 비용은 메인의 다음 질문과 개선 논의에 사용한다.

## 작은 작업으로 분해하기

큰 역할명만 배정하지 말고 **관찰 가능한 결과 하나**씩 맡긴다. 입력·인터페이스가 정해지고, 지정 파일 안에서 구현·검증해 완료를 판단할 수 있는 크기가 좋다. 여러 중요한 선택이 섞인 과제는 나누고, 단순 명령 하나로 끝나거나 전달 비용이 더 큰 일은 메인이 직접 한다.

| 필요한 결과의 예 | 작은 배정 예 | 먼저 정할 경계 |
| --- | --- | --- |
| 입력 오류 거절 | 지정 검증 함수의 빈 값·형식 오류 처리와 검사 | 입력 규격, 오류 형태, 담당 파일 |
| API 기능 하나 | 한 엔드포인트의 입력·응답·오류 계약 구현 | 경로/메서드/스키마, 의존 함수, 저장 책임 |
| 화면의 한 동작 | 폼의 제출 중·성공·실패 상태 처리 | API 계약, 상태 전이, 템플릿/스크립트 소유권 |
| 독립적인 확인 | 정해진 중복 요청 정책의 검사 준비·실행 | 실제 정책, 검사 파일, 실행 가능한 시점 |
| 읽기 전용 탐색 | 특정 입력을 읽는 함수와 호출 경로 찾기 | 검색 범위, 근거 위치, 수정 금지 |

실제 필요한 기능만 맡긴다. 같은 파일이 필요한 과제는 순서를 정하고, 병렬화를 위해 불필요한 파일 분리나 아키텍처 변경을 하지 않는다.

### 짧은 작업 지시

현재 대화나 기존 작업 기록을 사용한다. 과제마다 새 문서를 만들 필요는 없다.

```text
작업 ID / 현재 계약·결정 버전:
완료할 결과 하나 / E2E에서 연결할 위치:
읽을 입력·근거 / 필요한 선행 결과:
수정 허용 파일과 소유자 / 읽기 전용 범위:
확정된 입력·출력·인터페이스 / 아직 미정인 기준:
완료 조건 / 확인할 명령·관측:
시간·수정 예산(전체 잔여에서 차감) / 멈추고 반환할 조건:
반환: 적용 버전·변경 파일·결과·실행 증거·미검증·통합 필요사항
```

작업자는 새로운 업무 기준, 범위 밖 수정, 공통 파일 또는 인터페이스 변경이 필요하면 위치·이유·영향을 메인에게 전달한다. 빈 계약을 임의의 업무 사실로 채우지 않는다. 맡은 결과를 반환한 뒤 다른 기능이나 재위임을 임의로 시작하지 않는다.

## 결정 전달과 실행 조정

작업자는 메인과 사용자의 대화를 자동으로 공유받는다고 가정하지 않는다. 메인은 합의가 생길 때마다 영향받는 작업자에게 명시적으로 전달한다.

```text
결정 ID / 새 계약 버전 / 근거가 된 실제 답변:
바뀐 기준과 이유 / 유지할 필수 조건:
영향받는 작업·파일·인터페이스:
적용할 시점 / 중단·재작업할 기존 부분:
새 완료 조건과 재검증할 사례:
```

1. 준비된 독립 과제만 배정하고 파일 소유권을 확인한다. API 계약이 정해졌다면 화면·검사 준비는 구현과 병렬로 가능하지만, 실제 연결 검증은 선행 구현이 준비된 뒤 한다.
2. 메인은 논의 중에도 자연스러운 틈에 상태와 막힌 부분을 확인하고 완료 과제를 회수한다. 변하지 않은 상태를 반복 조회하거나 내부 명령을 중계하지 않는다. 사용자에게는 결정할 쟁점과 구현의 실제 진전을 짧게 설명한다.
3. 새 결정이 생기면 영향받는 과제만 조정한다. 필요하면 기존 과제를 중지하고 종료·변경 상태를 확인한 뒤 새 담당자에게 소유권을 넘긴다. 기존 작업자가 수정 중인 파일을 다른 작업자가 동시에 고치지 않는다.
4. 반환된 결과의 적용 버전을 확인한다. 오래된 결정에 따른 결과는 새 기준과 대조해 수정·재검증하기 전까지 통합 완료로 취급하지 않는다. 답변이 일부뿐이면 확인된 범위만 반영하고 나머지 의존 작업은 보류한다.
5. 메인이 실제 diff, 공통 상태, 실행 근거와 통합 결과를 확인한다. 남은 시간 안에서 유용하면 별도 읽기 전용 검토자에게 누락·반례·코드와 설명의 불일치를 확인하게 한다. 작업자의 완료 주장이나 개별 성공이 전체 E2E 성공을 대신하지 않는다.

모든 작업자의 실행·검증·수정·재배정·통합은 같은 전체 예산을 공유한다. 작업자를 추가하거나 잘게 나눠도 예산은 초기화되지 않는다. 기준을 충족하면 일찍 반환하고, 한도에 도달하면 실제 실패·미검증·안정본을 알린다. 기본 구조는 메인→작업자 한 단계이며 추가 위임은 메인이 범위와 잔여 예산 안에서 판단한다.

## 모델과 effort

아래는 역할별 선호이며 공식 모델 역할 규정이 아니다. 실제 제공 메뉴와 도구에서 지원하는 선택만 사용한다.

| 역할 | 기본 선택 | 조건 |
| --- | --- | --- |
| 메인 | 사용자가 선택한 모델·effort | 대화, 판단, 통합 책임 |
| 구현 작업자 | 6.1 Sol / medium | 독립 범위와 파일 소유권 확보 |
| 단순 분류·요약 작업자 | 6.0 Luna / 지원되는 low 또는 기본값 | 작고 명확한 읽기 전용 과제 |
| 다른 6.0 모델 | 실제 제공되는 선택 | 정확한 모델명과 작업자별 선택 지원을 확인한 경우 |

- 모델 이름을 임의의 API 식별자로 바꾸거나 더 최신 모델의 존재를 가정하지 않는다. 결정적인 파일 분류는 `rg`나 스크립트로 충분하면 먼저 사용한다.
- 작업자별 모델·effort 선택은 실제 도구가 지원할 때만 적용한다. 지원하지 않으면 현재 설정을 사용한다. 프롬프트에 적었다는 이유만으로 변경되었다고 말하지 않는다.
- 메인 설정은 임의로 바꾸지 않는다. 필요한 변경은 기존 안내 방식으로 사용자에게 추천하며, 작업자 설정을 메인 설정 변경으로 취급하지 않는다.
- 제공된 Codex 업데이트, 전역 설정 변경, 중첩 CLI 실행기나 새 AI·API·키 도입으로 병렬 기능을 우회하지 않는다.
- 속도는 관측한 모델 응답 대기·도구 대기·계산 시간으로 구분한다. 근거 없이 혼잡을 원인으로 정하거나 병렬 구성이 항상 더 빠르다고 보장하지 않는다.
