# 모델 배정과 병렬 작업 운영 기준

이 문서는 제공된 Codex 환경에서 적용할 프로젝트 선호 정책이다. 공식 모델별 역할 규정은 아니다.
기본 선호는 6.1 Sol과 가벼운 작업용 6.0 Luna다. 실제 메뉴·계정·도구에서 지원하는 선택만 사용하며, 더 최신인 모델이 제공된다고 가정하지 않는다.

## 모델과 effort 배정

| 역할 | 기본 선택 | 적용 조건 |
| --- | --- | --- |
| 메인 세션 | 6.1 Sol / medium | 사용자 대화, 판단, 통합 책임 |
| 구현 작업자 | 6.1 Sol / medium | 독립된 변경 범위와 파일 소유권 확보 |
| 단순 분류·요약 작업자 | 6.0 Luna / 지원되는 low 또는 기본값 | 범위가 작고 명확한 읽기 전용 작업 |
| 다른 6.0 모델 | 선택 사항 | 실제 메뉴의 정확한 모델명과 도구 지원을 모두 확인한 경우만 |

- 모델 이름을 임의의 API 식별자로 바꾸거나 없는 식별자를 만들지 않는다.
- 작은 파일 목록 분류처럼 결과가 결정적인 작업은 `rg`나 스크립트로 충분하면 먼저 사용한다.
- 작업자별 모델·effort 인자는 실제 도구가 지원하고 해당 환경에서 허용할 때만 사용한다.
- 프롬프트에 모델이나 effort를 적었다는 사실만으로 설정 적용을 인정하지 않는다. 도구 인자와 반환 정보 등 확인 가능한 근거를 남긴다.
- 작업자별 모델 선택이 없으면 같은 모델의 병렬 작업을 활용할 수 있다. 병렬 도구 자체가 없으면 순차 진행한다.
- 메인 세션의 모델·effort는 사용자의 실제 선택을 따른다. 변경이 필요하면 기존 안내 방식으로 추천하고 사용자가 직접 선택하게 한다. 워커별 선택을 메인 세션 변경으로 간주하지 않는다.

## 작업 시작과 사람의 확인

- 최초 문제 이해를 정리한 뒤 멈추는 단계와 기존의 모든 실제 사람 확인 지점을 유지한다.
- 사람의 응답을 기다리는 동안 다음 단계 작업을 백그라운드로 시작하지 않는다.
- 승인된 범위 안에서 크고 독립적인 작업 단위가 여러 개라면 소수의 작업자를 적극 활용한다.
- 약 2명으로 시작하되 실제 동시 실행 한도, 의존 관계, 통합 부담에 맞춰 조절한다. 인원은 고정 규칙이 아니다.

## 작은 작업으로 분해하기

사용자와 합의하는 작업 단위는 사람이 이해할 수 있는 하나의 결과다. 그 안을 여러 작은 작업자 과제로 나누되 범위·완료 기준·총예산·사용자 확인 지점은 그대로 유지한다. 내부 과제를 배정할 때마다 사용자에게 다시 승인받지는 않는다.

- 메인은 큰 역할명만 배정하지 말고 관찰 가능한 결과 하나씩으로 나눈다. 입력·인터페이스가 정해지고, 허용 파일 안에서 구현/검증해 완료 여부를 확인할 수 있는 크기를 목표로 한다.
- 한 과제에 서로 독립된 기능이나 여러 중요한 선택이 섞이면 다시 나눈다. 반대로 단순 명령 하나로 끝나거나 분해·전달·통합 비용이 더 큰 일은 메인이 직접 처리한다.
- 먼저 실제 선행 관계와 파일 소유권을 확인해 준비된 과제만 소수씩 병렬 실행한다. 작업자 수를 늘리는 것과 과제를 작게 만드는 것은 별개다. 모든 작은 과제를 한꺼번에 시작하지 않는다.

| 필요한 결과의 예 | 작은 배정 예 | 먼저 정할 경계 |
| --- | --- | --- |
| 입력 오류 거절 | 지정 검증 함수에 빈 값·형식 오류 처리와 관련 검사 추가 | 실제 입력 규격, 오류 형태, 담당 파일 |
| API 기능 하나 | 합의한 한 엔드포인트의 입력·응답·오류 계약 구현 | 경로/메서드/스키마, 의존 함수, 저장 책임 |
| 화면의 한 동작 | 지정 폼의 제출 중·성공·실패 상태 처리 | API 계약, 상태 전이, 템플릿/스크립트 소유권 |
| 독립적인 확인 | 정해진 중복 요청 정책에 대한 검사 작성·실행 | 실제 정책, 재현 수단, 별도 검사 파일과 실행 가능 시점 |
| 읽기 전용 탐색 | 특정 입력을 읽는 함수와 호출 경로 찾기 | 검색 범위, 근거 위치, 수정 금지 |

예시는 실제 기능이 있을 때만 적용한다. 같은 파일을 고쳐야 하는 예시들은 동시에 맡기지 않는다. 병렬화를 위해 불필요한 파일 분리나 새 아키텍처를 만들지 않는다.

## 짧은 작업 지시 형식

아래 내용은 현재 대화나 기존 작업 기록에 적으면 된다. 과제마다 새 문서를 만들 필요는 없다.

```text
작업 ID / 현재 합의 단위:
완료할 결과 하나:
읽을 입력·근거 / 필요한 선행 결과:
수정 허용 파일과 소유자 / 읽기 전용 범위:
확정된 입력·출력·인터페이스:
완료 조건 / 확인할 명령·관측:
남은 시간·이 과제에 배정된 수정 예산(전체 잔여에서 차감) / 멈추고 반환할 조건:
반환: 변경 파일·핵심 결과·실행 증거·미검증·메인이 할 통합
```

작업자는 범위 밖 수정, 새로운 업무 기준 또는 인터페이스 변경이 필요하면 그 위치·이유·영향을 메인에게 반환한다. 빈 계약을 임의의 업무 사실로 채우지 않는다.

## 실행·회수·재배정

1. 메인이 의존 관계를 확인하고 준비된 과제와 파일 소유자를 정한다. 미정인 업무 답변·입출력 계약에 의존하면 그 결정까지 기다린다. 계약이 이미 확정됐다면 별도 파일의 UI·검사 코드는 API 구현과 병렬로 준비할 수 있다. 실제 연결·실행·통합 검증은 필요한 구현과 실행 환경이 준비된 뒤 수행한다. 구현 결과가 있어야 알 수 있는 값은 미리 만들어내지 않는다.
2. 독립 파일의 준비된 과제만 병렬로 실행한다. 같은 파일의 다음 과제는 앞 작업의 변경을 메인이 확인하고 소유권을 넘긴 뒤 진행한다.
3. 작업자는 맡은 결과를 구현·확인하고 반환한다. 완료 뒤 다른 과제를 임의로 고르거나 추가 작업자를 연쇄 생성하지 않는다.
4. 메인은 실제 변경과 실행 근거를 확인하고 필요한 통합을 수행한다. 공통 파일·의존성·상태는 메인이 조정하며 통합된 현재 상태에서 관련 검사를 한다.
5. 완료한 작은 결과와 중요한 관측은 짧게 알린다. 기존 사용자 체크포인트에서는 대표 값과 전체 결과를 설명하고 실제 답을 기다린다.

모든 작업자의 실행·검증·수정·재배정·통합은 같은 사용자 작업 단위의 총예산을 공유한다. 메인은 과제별로 배정한 수정 예산의 합이 전체 잔여 예산을 넘지 않게 관리한다. 작업자를 추가하거나 다시 나눠도 예산은 초기화되지 않는다. 기준을 충족하면 일찍 멈추고, 한도에 도달하거나 막히면 근거·남은 문제·안정본을 반환한다. 기본 구조는 메인→작업자 한 단계이며, 추가 위임이 필요한 경우 메인이 현재 범위와 남은 예산 안에서 판단한다.

## 소유권과 통합

- 메인은 사용자 대화, 중요한 선택의 정리와 실제 사용자 결정 확인, 공통 설정, 통합, 실제 변경 diff 검토와 필요한 통합 검증을 책임진다.
- 예를 들어 프런트엔드, 백엔드, 검증을 독립적으로 나누되 각 작업자의 수정 파일과 경계를 먼저 지정한다.
- 같은 파일을 여러 작업자가 동시에 수정하지 않는다. 공통 파일 변경이 필요하면 메인에게 요청한다.
- 별도 검토자는 읽기 전용으로 두고 결함, 누락, 근거를 반환하게 한다.
- 작업 지시는 필요한 목표, 입력, 허용 파일, 완료 조건만 포함한다. 관련 없는 전체 맥락을 반복 전달하지 않는다.
- 작업자 반환 형식은 변경 파일, 수행한 검증과 증거, 발견한 문제, 다음 통합 조치로 통일한다.
- 메인은 작업자의 완료 보고만 믿지 않고 실제 diff와 통합 결과를 확인한다.

## 환경 제약과 속도 진단

- 병렬 실행을 우회하려고 중첩 CLI 실행기를 만들거나 새 API·AI·서비스·키를 도입하지 않는다.
- 전역 설정을 바꾸거나 제공된 Codex를 업데이트하지 않는다.
- 지연은 관측된 모델 응답 대기, 도구 대기, 계산 시간으로 구분해 기록한다.
- 관측 근거 없이 혼잡을 원인으로 추측하거나 특정 모델·병렬 구성이 항상 더 빠르다고 보장하지 않는다.
