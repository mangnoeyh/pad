# 웹 입력과 상태 변화의 예외 검증

실제 웹 기능의 구현·수정 단위에서 필요한 항목을 고른다. 현재 합의한 범위·대기 지점과 허용 도구를 유지한다. 없는 기능이나 새 프레임워크를 추가하지 않으며, 아래 사례 수를 채우는 것 자체를 목표로 삼지 않는다.

## 먼저 처리 정책을 정한다

입력·조건 변경과 오래 걸리는 작업이 있다면, 시작할 때의 `입력 버전·설정 버전·정책 버전` 묶음, 처리 중 상태, 완료 결과를 적용하는 조건을 정한다. 진행 중 같은 요청은 거절할지, 기존 작업을 조회하게 할지, 순서대로 처리할지, 취소 후 교체할지는 실제 요구사항에 따른다. 정해지지 않은 중요한 선택은 이유와 추천을 설명하고 사용자의 결정을 받는다. 이미 합의된 선택은 반복해서 묻지 않는다.

하나의 작업이 읽는 입력과 조건은 작업 도중 바뀌어 섞이지 않아야 한다. 결과에는 실제 사용한 조건과 버전이 연결되어야 하며, 이전 조건의 결과를 현재 조건의 결과로 표시하지 않는다. 이전 유효 결과를 보존하는 것과 새 조건에 대한 최신 결과로 채택하는 것을 구분한다.

설정 편집, 설정 저장, 계산 실행 요청은 구분한다. 변경 시 자동 실행하는지 실행 버튼을 누르는지는 실제 제품 계약에 따르며, 여기서 자동 처리는 접수한 계산을 개발자·AI의 개별 개입 없이 수행한다는 뜻이다. 최신값 자동 반영 정책에서 `재계산 필요`만 표시하고 끝내지 말고 후속 계산의 예약·실행·실패를 추적한다. 버튼 실행 계약에서는 아직 요청하지 않은 편집만으로 계산할 필요는 없으며, 이미 접수한 요청이 중복·교체 정책에 맞게 처리되는지 확인한다.

계정·자료·조회 대상이 바뀌는 화면은 **응답을 받을 수 있음**과 **지금 화면에 적용해도 됨**을 구분해 구현한다. 요청 당시 로그인 주체/세대를 확인하고, 데이터·오류 표시와 진행 표시 해제에는 자료·대상 범위와 조회 순서도 대조한다. 이전 세션의 성공 응답이 옛 화면을 되살리거나, 늦은 401/403·실패가 새 계정의 정상 상태를 지우지 않아야 한다. 반면 현재 로그인 주체·세대에 유효한 인증 실패는 조회 대상이나 순서가 바뀌었다는 이유만으로 누락하지 않는다. 인증 만료와 대상별 접근 거부는 실제 API 계약과 오류의 세션·대상 범위로 구분한다. 요청을 취소했다는 사실만으로 이미 도착 중인 응답까지 무효화됐다고 가정하지 않는다. 이 화면 보호는 서버 권한 검사를 대체하지 않는다.

세션 만료는 상세 조회·변경 요청·후속 상태 조회 중 어디서 발생해도 같은 복구 계약을 따른다. 세대를 바꾸면 이전 요청의 `finally`가 실행돼도 조건 검사 때문에 정리를 건너뛸 수 있다. 무효화한 요청이 보유하던 진행 표시·입력 잠금도 세션 종료 시 정리해 다시 로그인하고 정상 작업을 시작할 수 있게 한다. 반대로 옛 요청의 정리가 새 세션의 진행 중 작업을 풀어 버리면 안 된다. 인증 화면으로 이동했다는 사실만으로 복구 완료를 판정하지 않는다.

사용자 동작 자체가 세대·버전을 바꾸는 경우에는 그 동작의 성공·실패·정리가 어느 새 식별자를 소유하는지 먼저 정한다. 공통 실행 래퍼가 변경 전 식별자를 잡고 내부 동작이 이를 갱신하면, 현재 시도의 거절이나 오류까지 오래된 응답으로 잘못 버릴 수 있다. 옛 응답을 막는 검사와 함께, 현재 로그인·전환 시도가 실패했을 때 이유가 표시되고 수정 후 재시도되는지도 원래 이벤트 경로에서 확인한다.

변경 접수와 뒤이은 상태 조회는 별도 상태로 설계한다. 접수가 확인되면 식별자와 처리 사실을 먼저 보존하고, 조회만 실패했을 때는 그 식별자를 보여 주며 조회를 다시 할 경로를 남긴다. 입력을 영구 잠그거나 새 변경 요청을 보내는 방식으로 복구를 대신하지 않는다. 접수 자체가 불확실한 경우의 동일 작업 재시도와 구분하고, 이 계약을 화면 담당자의 완료 기준에도 전달한다.

## 설정 가능한 계획 서비스의 실행 경로를 확인한다

허용된 관리자 설정이나 입력 자료 변경 뒤에는 합의한 실행 방식에 따라 접수한 재계산 요청을 서비스 안에서 계획 생성·필요한 보정·전체 검증까지 자동 처리한다. 설정 편집·저장 자체가 계산 요청인지는 위의 실행 계약을 따른다. 개발 중 정책을 합의하는 절차를 운영 중 매번 개발자 수정이나 수동 예외 승인을 받는 절차로 옮기지 않는다. CLI 수작업이나 LLM 호출도 실제 실행 계약에서 요구하지 않는 한 정상 처리의 필수 단계로 두지 않는다. 승인 범위를 벗어나는 변경과 필수 제약의 완화는 이 자동 처리 권한에 포함되지 않는다.

- 화면/API에 보낸 실제 설정과 자료가 작업 스냅샷, solver, 보정, validator, 저장 및 내보내기까지 전달되는지 추적한다. 각 단계가 같은 버전 묶음을 사용하고, 현재 용량·한도·입력 대신 초기 기본값이나 이전 결과를 읽지 않는지 실행 근거로 확인한다. 설정 저장이나 화면 숫자 변경만으로 통과시키지 않는다.
- 대표 설정 `A → B → A`에서 B는 실제 제약의 작동을 확인할 수 있는 다른 허용 값으로 정하고, 최소 한 가지 의미 있게 변경한 입력 자료도 검사한다. 결과·검증·내보내기가 현재 조건을 만족하는지 확인하고, 같은 설정으로 돌아오면 그 설정의 불변 조건이 다시 성립하는지 본다. 비결정적 solver의 배정 문자열이나 결과 전체가 이전과 완전히 같아야 한다고 요구하지 않는다.
- 일반 규칙으로 승인된 예외는 현재 입력·정책과 최종 배정 구성원으로 자격을 계산한다. 명시적으로 고정 명단만 승인한 경우와 구분한다. 재배정·보정 후 자격과 예외 전체를 함께 재검증하고, 조건이 사라진 대상의 이전 자격이 회수되는 사례를 확인한다. 정책 범위 안의 예외 선택과 보정이 수동 승인 없이 완료되는지도 본다.
- 필수 제약은 모든 경로에서 유지한다. 불가능을 입증한 경우와 시간/탐색 한도에 도달해 아직 해결하지 못한 경우를 다른 상태로 반환한다. 검증에 실패한 부분 결과를 성공으로 저장·적용·내보내지 않으며, 유효한 결과도 별도 입증 없이 최적성까지 입증한 것으로 표시하지 않는다.

## 관련 예외를 골라 상태까지 확인한다

| 상황 | 관측할 내용 |
| --- | --- |
| 누락·null·빈 값·잘못된 숫자나 날짜·기간 역전 | 실제 요청 경계에서 필수 필드·자료형을 검사한 뒤 기본값이나 내부 함수를 적용한다. 누락/null, 유효한 0·false, 명시적 기본값 복원은 계약상 다른 의미일 수 있으므로 편의용 기본 인자로 합치지 않는다. 잘못된 저장 요청이 복원·삭제 등 다른 정상 동작으로 성공하지 않고 현재 입력·결과를 보존하는지 직접 API 요청에서도 확인한다. 임의의 업무 상한을 만들지 않는다. |
| 연속 클릭·두 탭/클라이언트의 동시 요청 | 합의한 정책에 맞는 작업 수·계산 횟수·저장 횟수·반환 ID. 버튼 비활성화만으로 서버 중복 차단을 입증하지 않는다. |
| 접수 기록 저장 실패 | 진행 중 표시나 잠금을 잡은 직후, 접수가 저장되기 전에 실패를 한 번 일으킨다. 이전 결과와 저장된 작업 수를 확인하고 장애를 해제한다. 같은 서버에서 새 요청이 처리되는지 확인해 유령 작업이나 남은 잠금을 찾는다. |
| 처리 중 조건 또는 입력 자료 변경 | 접수한 입력·설정·정책 스냅샷, 진행 중 작업과 새 조건의 관계, 결과 적용 가능 여부. 응답을 잠시 보류한 상태에서 실제 입력창·자료 선택·파일 읽기 경로로 변경을 시도한다. 편집을 막는 정책이면 해당 입력들도 실제로 잠기는지 확인하고, 편집을 허용하면 나중 응답이 새 초안을 조용히 덮어쓰지 않게 보존·구분한다. 잠그기 전에 시작된 파일 읽기 등 비동기 입력이 잠근 뒤 도착하는 순서도 확인한다. 미래 동작의 비활성화만으로 이미 진행 중인 작업을 취소·무효화했다고 보지 않는다. 입력창 값과 계산에 쓴 값이 달라지면 명확히 표시한다. |
| 이전 요청이 나중 요청보다 늦게 완료 | 화면 표시와 서버의 현재 결과 지정·저장을 각각 확인한다. 최신 버전 확인과 결과 채택 사이의 경합까지 재현하고 서버의 조건부 갱신이 원자적인지 본다. 화면에서 오래된 응답을 무시해도 서버의 덮어쓰기가 막혔다고 가정하지 않는다. |
| 서버 오류·통신 끊김·시간 초과·예상과 다른 응답 형식 | 오류/진행 상태와 재시도 안내, 입력 유지, 부분 결과 노출 여부. 클라이언트 시간 초과만으로 서버 작업도 실패했다고 단정하지 않는다. 재시도가 같은 논리 작업인지 새 작업인지의 정책과 식별 방식을 확인하고, 새 ID로 재요청해 중복 차단을 우회하는지 검사한다. |
| 접수 직후 첫 상태 조회만 실패 | 접수된 식별자를 보존한 채 같은 작업을 다시 조회한다. 생성·등록의 성공과 뒤이은 조회 실패를 따로 표시한다. 같은 폼을 다시 눌렀을 때 새 항목이 생기는지, 사용자가 의도한 새 등록은 가능한지 확인한다. 첫 조회와 정기 조회 중간에 각각 한 번 끊어 보고, 자동 조회를 중단하면 현재 작업과 수동 확인 방법을 표시한다. |
| 자료 교체와 재시도가 함께 있는 경우 | 같은 사용자가 같은 내용으로 다시 보냈을 때, 같은 키로 다른 내용을 보냈을 때, 자료 교체 뒤 옛 화면에서 재시도했을 때를 구분한다. 성공 응답의 식별자가 어느 자료에 속하는지 실제 조회로 대조한다. 옛 요청의 처리 사실과 새 자료에 반영됐다는 응답을 구분하고, 새 화면에서 의도한 작업은 정상 실행되는지 확인한다. |
| 미확인 동작을 남기고 계정 전환 | A의 접수 여부가 미확인일 때 B로 로그인해 B의 새 작업을 시도한다. A의 내용이나 접수가 B에게 넘어가지 않고 B의 정상 작업이 진행되는지, A가 돌아왔을 때 자신의 동작을 복구할 수 있는지 확인한다. |
| 계정 전환 후 이전 요청의 성공·오류가 늦게 도착 | A의 조회 응답을 보류한 채 로그아웃·B 로그인을 마친 뒤 전달한다. 옛 상세·설정·요약이 B 화면에 섞이지 않고, 옛 인증 오류가 B를 로그아웃시키거나 새 오류 상태로 덮지 않는지 확인한다. B의 정상 후속 조회도 함께 확인한다. 역할이 같은 서로 다른 계정도 같은 경계가 필요하다. |
| 요청 처리 중 현재 세션이 만료 | 상세 조회와 접수 후 첫 조회에서 각각 실제 만료 응답을 처리한다. 옛 데이터가 지워지고 로그인 입력·제출이 다시 가능하며, 재로그인 후 새 요청이 정상 처리되는지 확인한다. 이전 요청의 늦은 정리가 새 요청의 잠금을 건드리지 않는지도 본다. 대상별 접근 거부는 API 계약에 따라 별도로 검사한다. |
| 접수 여부가 불확실한 상태에서 다시 충돌 | 잠시 다른 작업이 진행 중인 경우와 입력·권한·자료 범위가 달라져 요청을 고쳐야 하는 경우를 구분한다. 같은 HTTP 상태 코드라도 복구 방법이 다르면 응답 사유로 구별한다. 일시 충돌이 풀린 뒤 기존 동작 식별자로 재시도해 같은 항목이 한 번만 저장되는지 확인한다. |
| 새로고침·화면 이탈 후 복귀 | 실제로 약속한 작업 조회/복구 동작, 중복 시작 여부, 화면과 서버 상태 일치. 지속 실행이나 복구 기능이 요구되지 않으면 그 한계를 밝힌다. |
| 계산 후 저장·결과 적용 단계 실패 | 기존 유효 결과 유지, 부분 저장/반쯤 갱신된 화면 방지, 실패 후 재요청의 처리. 검증된 결과·검증 근거·버전·내보내기 대상이 화면과 서버에서 일관되게 채택되도록 원자적 적용이나 실제 저장 구조에 맞는 복구를 확인한다. |
| 취소 또는 교체가 제공되는 경우 | 취소 요청과 취소 완료를 구분하고 완료 직전 취소·늦은 완료·교체 작업과의 관계를 본다. 브라우저 요청 중단을 서버 취소나 저장 롤백의 증거로 삼지 않는다. |
| 권한이 구분되는 경우 | 다른 역할로 직접 보낸 변경 요청이 거절되고 저장 상태가 유지되는지 확인한다. 서로 다른 두 계정으로 같은 실행 결과를 조회하고 한 계정만 볼 수 있는 식별자·값이 다른 계정의 실제 응답 본문에 포함되는지 검사한다. 행 목록 외에 중첩된 요약·후보 설명·이력·내보내기도 각 경로의 공개 범위대로 검사한다. 역할별 응답은 필요한 필드로 구성하고 계산에 분석 필드를 추가한 뒤 같은 검사를 다시 실행한다. |

## 확인 방법과 우선순위

- 손실·중복 저장·허용되지 않은 상태 변경·잘못된 결과 적용을 우선하고, 오류 후 복구와 화면 안내를 이어 확인한다. 외형 점검이 핵심 데이터 검증을 대신하지 않는다.
- 허용된 테스트 수단으로 두 요청이 실제 겹쳤음을 관측한다. 가능한 경우 테스트의 제어 지점에서 완료 순서나 저장 실패를 재현한다. 빠르게 연속 호출했다는 이유만으로 동시 실행 경합을 검사했다고 쓰지 않는다.
- 재시도 검사는 실제 폼이나 버튼 핸들러에서 출발해 보낸 요청의 횟수·식별자와 저장된 건수를 함께 기록한다. 접수·저장 성공 뒤 이력이나 상태 조회가 이어진다면 **변경 요청은 성공시키고 뒤의 조회만 실패**시킨 뒤 화면이 안내한 복구를 같은 이벤트 경로에서 실행한다. 성공 식별자와 표시가 유지되고 복구가 새 변경 요청·중복 저장을 만들지 않는지 확인한다. 테스트가 서버에 같은 키를 직접 두 번 넣은 결과만으로 화면도 그 키를 재사용한다고 판단하지 않는다. 실제 화면을 조작할 수 없으면 구현에 맞는 경로를 고른다. 서버가 렌더링한 일반 폼은 실제 HTML 필드·쿠키·제출 응답의 이동 주소로 HTTP 요청과 저장 결과를 대조하고, 자바스크립트 화면은 허용된 범위에서 원래 이벤트 코드를 실행해 대체한 DOM·통신 범위를 밝힌다. 검사 때문에 없는 클라이언트 상태 구조를 추가하지 않으며, 두 방법 모두 실제 브라우저 이동·캐시·레이아웃 검증을 대신하지 않는다.
- DOM·통신을 대체하는 검사에서는 해당 주장에 영향을 주는 선택자 결과·입력 종류·이벤트·응답 순서를 원래 HTML/코드와 맞춘다. 예를 들어 버튼 선택자가 테스트에서 모든 입력을 반환하면 실제 잠금 누락을 가릴 수 있다. 먼저 고장 난 원래 경로에서 기대와 다른 결과가 재현되는지 보고, 같은 관측 조건으로 수리본을 확인한다. 대체 환경의 편리한 동작을 제품의 보장으로 세지 않는다.
- 실제 실행 구성의 범위를 확인한다. 한 화면 또는 한 프로세스 안의 플래그/잠금이 여러 클라이언트·프로세스·서버 전체를 보호한다고 추정하지 않는다. 기존 구성에 맞는 최소 해결을 택하며 무조건 큐·분산 잠금을 도입하지 않는다.
- 저장되는 변경 작업에서 접수·성공 여부가 불확실해질 수 있다면, 성공 결과를 저장한 직후 응답 전송만 실패시키고 새 연결에서 같은 작업을 조회한다. 실제 commit 뒤에도 실패 응답/로그/화면이 ‘미저장·계산 실패’라고 단정하지 않고, 이미 저장된 식별자로 조회·복구하며 중복 생성하지 않는지 확인한다. 저장 상태, 예외를 잡는 범위, 사용자가 읽는 안내를 함께 대조한다. 계산 전 실패·저장 전 실패와는 별도로 검사한다.
- 관련 함수/API와 저장 상태를 함께 검사하고, 사람이 허용된 미리보기에서 확인한 화면은 그 관측을 별도로 남긴다. 자동 화면 조작은 해당 환경에서 허용될 때만 쓴다.
- 사례마다 `시작 상태·조건/버전 → 요청 순서 → 기대 정책 → 실제 응답·작업 상태·저장 결과 → 근거`를 기록한다. 임시 검사 자료를 정리하기 전에 핵심 주장을 재검산할 실제 입력·설정·저장 결과·내보내기 중 필요한 최소 근거를 새 로컬 경로에 보존한다. 통과 로그만 남기고 유일한 결과를 지우지 않으며 이전 증거는 덮어쓰지 않는다. 정상 복구 후 기존 경로가 여전히 동작하는지도 확인한다. 통과·실패·미실행·해당 없음을 구분한다.

보고서나 코드 주석에 처리한다고 적혀 있다는 사실만으로 실행 통과를 선언하지 않는다. 해설에는 실제 선택한 정책·구현 위치·재현 결과·남은 제한을 연결한다.
