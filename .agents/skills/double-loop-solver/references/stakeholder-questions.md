# 숨은 운영 요구와 담당자 질문

사용자와 문제의 의미·최적화 기준을 논의할 때 적용한다. 메인은 명시된 조건을 통과하는 것과 실제로 쓸 만한 결과를 만드는 것을 함께 살핀다. 담당자 답변을 한 번 받았다고 모든 기준이 확정됐다고 보지 않는다. 단순 질문 문안 편집만 요청받았다면 원래 목적·우선순위를 보존하고, 이 문서로 조사 범위를 늘리지 않는다.

## 사실에서 질문으로

원문 요구, 자료 설명, 실제 입력·출력, 기존 답변을 먼저 읽는다. 첫 결과와 각 개선 결과에서 아래 관점의 관련성을 짧게 훑는다. 목표 우선순위를 합의했어도 다른 관점을 조사한 것으로 세지 않는다. 해당하는 항목만 기존 작업 기록에 남기며, 모든 항목을 질문하거나 새 기능으로 만드는 것은 아니다.

| 관점 | 결과에서 확인할 근거 |
| --- | --- |
| 사용자와 실제 업무 결과 | 누가 결과로 어떤 결정을 하는가. 합계가 좋아도 실제로 사용할 수 없는 행·상태·화면이 있는가. |
| 데이터와 현실의 차이 | 측정값·추정치·누락을 구별했는가. 근사 오차가 결과 순서나 허용 여부를 바꾸는 경계 사례가 있는가. |
| 병목과 자원 낭비 | 오래 걸리거나 자원을 많이 쓰는 대표 사례의 원인은 무엇인가. 같은 처리 범위·상위 품질을 유지하며 더 적게 쓸 대안이 있는가. |
| 긴 대기와 반복되는 부담 | 평균 밖의 큰 손실, 같은 대상의 반복 손실, 자료에 실제 존재하는 집단별 분포는 어떤가. 전체 개선이 누구의 부담 증가를 동반하는가. |
| 조건 변경과 실패 뒤 사용 | 새 입력·설정에서 정책이 자동 적용되는가. 부분 처리·재시도·이전 결과가 사용자에게 어떤 상태로 보이고 실제로 저장되는가. |

관련 관점은 `관점 | 확인할 현상 | 상태·근거 | 다음 행동` 정도로 기존 기록에 묶는다. 상태는 `미조사 / 근거 부족 / 확인 / 보류 / 해당 없음`으로 구분하고, 보류·해당 없음에는 이유를 붙인다. `확인`은 해당 주장에 필요한 관찰을 했다는 뜻이며 개선 완료나 문제가 없다는 뜻은 아니다. 설명문·지표 필드·질문 문안을 만들었다는 사실만으로 측정·답변 수신·구현·검증을 대신하지 않는다.

집단별 분석은 제공된 속성과 범위에서만 한다. 없는 집단을 추정하거나 개인정보를 추가 수집하지 않는다. 대기와 완료 지연처럼 의미가 다른 지표를 섞지 않고, 집단별 대상 수와 긴 부담·반복 손실을 실제 행에서 확인한다. 이용률·평균을 쓰면 단위·분모·처리 범위를 확인하고, 대상 제외나 분모 축소로 좋아진 수치를 전체 개선으로 읽지 않는다. 편중을 발견해도 공정성 가중치·대기 상한을 임의로 필수 조건에 추가하지 않는다.

발견한 항목은 **실제 입력·출력의 관찰과 근거 → 업무상 비용·불편·실패 → 아직 모르는 기준 → 그 기준을 확인할 질문**으로 설명한다. 관찰한 행·집계·사례와 단위·분모를 필요한 만큼 연결해 왜 지금 답이 필요한지 보여준다. 관찰 전에는 가설이라고 표시하고, 실제 수치나 문제라고 꾸미지 않는다. 모든 가능성을 미리 조사하기보다 최초 기준본, 이상한 결과, 새 답변이 나온 시점에 관련 가정을 다시 본다.

각 기준의 성격을 구분한다.

- **명시된 필수 조건:** 근거 위치와 적용 범위를 기록한다. 사용자의 선호만으로 완화하지 않는다.
- **운영 목표·선호:** 비용·품질·효율 사이에서 무엇을 우선할지 논의한다. 보기 나쁜 결과를 발견했다고 새 강제 조건을 임의로 추가하지 않는다.
- **임시 가정:** 확정되지 않은 부분과 예상 영향을 표시한다. 사용자에게 위임받은 범위의 되돌리기 쉬운 가정만 기준본에 쓰고, 공식 답변처럼 기록하지 않는다.
- **미확인 사실·충돌:** 답이 필요한 주체와 근거를 남긴다. AI나 사용자의 추측으로 담당자의 답을 대체하지 않는다.

## 답을 얻을 수 있는 작은 질문 묶음

질문 우선순위는 정답·필수 조건을 바꾸는 모호함, 큰 운영 손실, 구현의 되돌리기 어려운 선택 순으로 잡되 실제 영향과 남은 시간에 맞춘다. 관찰마다 먼저 누가 무엇으로 답할 수 있는지 정한다.

| 필요한 답 | 다음 행동 |
| --- | --- |
| 업무 사실·실제 운영 규정·허용 범위 | 자료와 기존 답을 확인한 뒤 담당자에게 질문할 문안을 준비한다. |
| 규정이 없고 아직 결정·위임되지 않은 절충 | 실제 대안과 이득·부담을 쉽게 설명하고 사용자에게 중요한 선택 하나를 묻는다. 이미 정한 기준이나 위임 범위는 다시 승인받지 않는다. |
| 구현 원인·대안의 성능·주장한 불가능 여부 | 메인이나 워커가 실행·검산한다. 담당자에게 알고리즘의 우열을 대신 결정하게 하지 않는다. |

지금 결과를 가장 크게 바꿀 담당자 질문 한 건을 우선 제안한다. 서로 분리하면 답하기 어려운 세부 기준만 짧게 묶고, 나머지는 기록에 둔다. 관찰한 사례 또는 명시한 가설, 답에 따라 달라질 자동 정책·검증 대상, 답이 없을 때 유지할 미확인 상태를 함께 정한다. 질문 수를 채우지 않으며 자료에 답이 있는 부분은 묻지 않는다.

사용자에게는 왜 답이 필요한지와 영향받는 작업을 짧게 설명한다. 담당자에게 전달할 문안은 보통 다음 정도면 충분하다.

> 현재 자료/답변에서는 …로 이해했습니다. 그런데 …인 사례에서는 A와 B의 결과가 달라집니다. 이 경우 어떤 기준을 적용해야 하나요? 기준의 적용 대상과 예외도 알려 주세요.

선택지를 주더라도 그 밖의 답을 막지 않는다. “효율을 높여도 되나요?”처럼 어떤 구현에도 맞는 포괄적 허락보다, 결과를 가르는 실제 사례·경계값·비교 기준을 묻는다. 실행·연결 문제는 제공 환경의 지원 채널로 구분한다.

메인은 문안을 정리하고 **사용자가 허용된 담당자에게 전달**한다. 질문 준비만으로 직접 연락·메시지 발송·외부 조사 권한을 얻지 않는다. 환경이 허용한 채널과 자료 범위를 지키며, 답변은 사용자가 전달한 실제 내용으로만 기록한다.

## 답변을 받으면 후속 질문까지 이어가기

1. 실제 답과 출처를 보존하고, 각 질문을 `해결 / 일부 해결 / 미확인 / 충돌`로 구분한다. 관련된 말만 받았거나 적용 범위·단위가 빠졌다면 해결로 닫지 않는다.
2. “확정된 부분은 …이고, 아직 …가 빠졌다”고 사용자에게 짧게 설명한다. 모호한 답을 수치 기준이나 구현 규칙으로 임의 번역하지 않는다.
3. 남은 부분이 결과를 바꾸면 **이미 받은 답을 짧게 확인하고, 빠진 한 기준을 구체적 사례로 좁힌 후속 문안**을 바로 제안한다. 원래 질문 전체를 반복하거나 답한 부분을 다시 묻지 않는다.
4. 담당자 답이 원문·이전 답과 충돌하면 두 근거와 결과 차이를 제시하고 적용 범위를 확인한다. 최신 답이라는 이유만으로 상위 지시를 덮어쓰지 않는다.
5. 실행 가능한 기준이 되면 사용자와 필요한 선택만 정하고, 결정·근거·적용 범위·검증할 사례를 워커에게 명시적으로 전달한다. 기존 결과와 검사에 미치는 영향도 확인한다.

고정 횟수로 질문을 끝내거나 무한히 반복하지 않는다. 결정에 충분한 답을 얻었거나, 남은 정보의 영향이 작거나, 담당자가 더 답할 수 없거나, 질문·재구현 비용이 남은 시간을 넘으면 상태를 정리한다. 답이 없다는 이유로 “허용”이나 “문제없음”으로 간주하지 않는다. 중요한 미확정 사항은 사용자에게 선택지·한계를 제시하고, 확정이 필요한 부분만 보류한다.

## 질문 기회를 적극적으로 쓰기

메인은 원문을 처음 읽을 때뿐 아니라 첫 E2E 결과와 각 개선 회차에서 관점 기록·미답 항목·새 관찰을 다시 대조한다. 목표 순서를 정하는 질문에만 머물렀다면, 아직 조사하지 않은 관련 관점에서 실제 손실이나 경계 사례를 먼저 찾는다. 그 결과를 보고 질문·실험·보류 중 다음 행동을 고른다. 사용자가 질문을 더 만들라고 해야 시작하지 않으며, 확인할 업무 기준이 없으면 억지 질문 대신 검증할 가설과 이유를 설명한다.

짧은 답은 그 범위만 확인한 것이다. 예를 들어 “납기가 먼저”라는 답만으로 초과 **건수**와 초과 **총량**이 엇갈릴 때의 순서, 한 대상의 큰 부담과 여러 대상의 작은 부담, 비용과 대기의 교환까지 확정하지 않는다. 대안이 실제로 갈라지는 작은 사례·경계값을 보여주고 하나씩 좁혀 묻는다. 가중치·엄격한 우선순위·적용 범위가 결과를 바꾸면 그 차이를 일반 기술 선택으로 숨기지 않는다.

새 결과가 전반적으로 좋아져도 큰 손실이 남은 사례와 부담이 늘어난 대상을 비교한다. 기존 관행·예외·자동 조정의 범위가 그 결과를 바꾸는지 살핀다. 질문에 답을 받으면 관련 관점의 다음 행동과 영향을 받는 자동 정책을 갱신한다. 숨은 정보를 찾는다는 이유로 비공개 채점 기준이 있다고 단정하거나 원문과 충돌하는 제약을 만들지 않는다.

구체적인 기준이 확정되면 그 주제는 닫되, 새로운 결과나 입력이 적용 범위를 바꾸면 다시 연다. “모른다”, “그런 규정은 정하지 않았다”, “추가 답변 불가”를 구분해 기록한다. 확인된 규정 부재와 단순 미확인은 다르다. 담당자가 더 답할 수 없는 같은 질문을 반복하기보다 다른 중요한 미확인 사항을 탐색한다. 답변 수나 질문 횟수만으로 전체 개선을 완료하지 않으며, 개선 종료는 [회차 운영](improvement-rounds.md)의 실제 사용자 답을 따른다.

## 한 기록에서 결정과 구현을 연결하기

기존 작업 기록에 질문별로 아래 내용을 짧게 이어 남긴다. 별도 문서를 매번 만들 필요는 없다.

`Q-ID | 관찰·근거 | 확인할 결정과 영향 | 전달 문안 | 실제 답·출처 | 상태 | 다음 질문/가정 | 영향받는 작업자·파일 | 적용·재검증 결과`

사용자가 질문을 실제 보냈는지 모르면 `전달 문안 준비`로 기록한다. 답변 대기와 사용자 선택 대기를 구분한다. 사용자 대화가 워커에게 자동 공유된다고 가정하지 않는다. 변경된 기준과 확인용 사례를 보내고, 수신·적용 결과를 확인한다.

이미 허용된 E2E 구현은 질문과 독립적인 입력 읽기, 화면, 상태 처리, 입출력 연결 등을 가장 단순한 방법으로 계속 진행할 수 있다. 미정 의미에 의존하는 계산만 분리하고, 기존 확정 기준이나 허용된 임시 가정을 표시한 기준본을 보존한다. 질문 대기를 모든 워커의 정지 이유로 삼거나, 반대로 대기를 이용해 미정 최적화 기준을 몰래 확정하지 않는다. 실제 병렬 지속 여부는 실행 환경에서 확인한 범위만 보고한다.

## 짧은 예시

- **거리 근사:** 위치 좌표만 확인된 상태에서 직선거리 기반 값은 근사라고 표시한다. “실제 접근 시간을 반영해야 하나요?”라는 질문에 “현실적으로 계산해 주세요”라는 답만 왔다면, “연결망 자료를 사용할 수 있나요? 없을 경우 근사값 사용이 허용되는지, 기준 이하 여부가 바뀌는 경계 사례는 어떻게 처리할지”로 좁힌다. 데이터 확보 비용과 정확도 차이는 사용자에게 설명한다.
- **사용 효율:** 총 사용량과 처리 횟수로 계산한 평균이 낮다면 분모·집계 방식과 극단 사례부터 확인한다. 담당자가 “효율도 고려”라고 답해도 임의의 최소 사용량을 강제하지 않는다. “처리 횟수를 줄이기 위해 일부 대상의 대기를 늘려도 되는지, 허용 한계와 모든 대상 처리 의무는 무엇인지”를 확인한다. 개선 전후 효율뿐 아니라 대상 포함률·최악의 대기도 함께 비교한다.

예시는 발견 방법을 보여줄 뿐, 다른 과제에 같은 조건을 추가하라는 뜻이 아니다. 최종 설명에는 실제로 발견한 문제, 질문으로 확인한 기준, 사용자가 고른 절충, 적용 결과와 남은 불확실성만 남긴다.
