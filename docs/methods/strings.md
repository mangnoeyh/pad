# 문자열·패턴·식별자

먼저 문자열의 단위를 정한다. 바이트, Unicode code point, 화면에 보이는 한 글자, 단어는 서로 다르다. 검색에 쓸 정규화와 원본 표시값을 구분하고 원본 위치를 잃지 않는다. `n`은 본문 길이, `m`은 패턴 길이, `L`은 전체 패턴 길이 합, `z`는 출력 일치 수다. 아래 복잡도는 한 문자 비교가 상수 시간인 모형이다.

## 빠른 선택

| 요구 | 먼저 검토 | 추가 확인 |
| --- | --- | --- |
| 단순 포함·정확한 부분문자열 | 언어 내장 검색 | 빈 패턴·겹친 일치·문자 단위 |
| 긴 스트림의 한 패턴 | KMP·Z | chunk 경계와 원본 위치 |
| 접두어 사전 조회 | Trie | Unicode·메모리·동적 삭제 |
| 많은 패턴을 한 본문에서 찾기 | Aho–Corasick | 결과 개수 자체가 클 수 있음 |
| 고정 본문에 반복 검색 | suffix array 등 인덱스 | 구축 비용·본문 버전 |
| 유사 이름·오탈자 | 편집 거리·토큰 기준 | 자동 동일인/동일항목 판정과 구분 |
| 규칙 형식 검사 | 파서·정규식 | 전체 일치와 부분 일치 구별 |

## S01 — 내장 검색과 정규화

- **적용:** 일반 텍스트의 정확한 포함·접두어·접미어 검색은 설치 언어의 내장 기능부터 검토한다. 직접 구현보다 실제로 빠를 수 있으므로 대표 길이에서 측정한다.
- **의미:** 대소문자 통합, 공백 정리, NFC/NFKC 등은 서로 다른 문자를 같게 만들 수 있다. [Python Unicode 문서](https://docs.python.org/3/library/unicodedata.html)는 정규화 형식을 구분한다.
- **반례:** 표시가 같아 보이는 조합형·분해형 문자열의 code point 수가 다를 수 있다. 식별자에서 대소문자를 무조건 지우면 별개 대상을 합칠 수 있다.
- **검산·연결:** 원본·정규화 값·변환 정책을 구분하고, 정규화 후 위치를 원본 하이라이트에 바로 적용하지 않는다. 업무상 같은 항목인지 판단하는 규칙은 따로 확인한다.

## S02 — KMP와 prefix function

- **적용:** 패턴의 접두어/접미어 관계를 이용해 이미 비교한 부분을 건너뛴다. prefix-function 구현은 전처리 `O(m)`, 검색 `O(n+z)`, 보조 공간 `O(m)`.
- **장점:** 다음 chunk로 상태를 넘길 수 있어 스트리밍 검색에 적합하다. 모든 일치를 찾을 때 일치 직후의 상태 이동으로 겹친 일치도 유지한다.
- **반례:** `aaa`를 `aaaa`에서 찾으면 겹친 일치 두 개를 요구할 수 있다. 빈 패턴의 결과를 임의로 정하지 않는다.
- **검산:** 짧은 본문과 패턴의 모든 시작점을 직접 검사한 기준과 비교한다. [Princeton 문자열 검색 자료](https://algs4.cs.princeton.edu/53substring/)는 구현 변형에 따라 전처리 구조·비용이 달라질 수 있음을 보여준다.

## S03 — Z 알고리즘

- **적용:** 각 위치에서 전체 문자열의 접두어와 얼마나 일치하는지 `O(n)`에 계산한다. `패턴 + 구분자 + 본문` 구조로 패턴 일치를 찾거나 반복 구조를 검사한다.
- **조건:** 구분자는 입력에 없는 값이어야 한다. 임의 텍스트에서 특정 문자가 없다고 가정하기보다 토큰 배열과 별도 sentinel을 고려한다.
- **반례·검산:** 본문 속 구분자가 겹치면 경계를 넘어 일치가 이어질 수 있다. 모든 위치의 접두어 길이를 직접 비교해 검산하고 `Z[0]`의 정의를 호출부와 맞춘다.

## S04 — Trie·접두어 트리

- **적용:** 사전의 접두어 존재, 자동완성 후보, 계층 경로. 한 키 길이 `m`에 대해 문자 전이가 상수 시간일 때 삽입·조회 `O(m)`; 전체 노드 수는 총 키 길이에 비례할 수 있다.
- **조건:** 전이를 고정 문자 배열로 두면 문자 집합이 클 때 메모리가 크다. 맵 기반 전이의 비용과 Python 객체 수를 측정한다.
- **반례:** 키의 끝 표시가 없으면 `ab`와 `abc`의 존재를 구별하지 못한다. 한 키 삭제가 다른 키와 공유한 노드를 지우면 안 된다.
- **검산:** 정렬된 키 목록의 prefix 필터와 비교한다. 후보 전체 반환의 시간은 출력 수에도 비례한다. [저자 교재의 문자열 자료](https://algs4.cs.princeton.edu/50strings/)에서 trie와 검색의 목적 차이를 확인할 수 있다.

## S05 — Aho–Corasick

- **적용:** 여러 패턴을 하나의 본문에서 동시에 찾는다. trie와 실패 링크로 진행하며, 적절한 전이 표현에서 검색 `O(n+z)`가 가능하다. 구축 비용·공간은 전체 패턴 길이와 문자 집합/전이 표현에 달려 있다.
- **조건:** 한 상태에서 여러 패턴이 끝날 수 있고 실패 링크를 따라 종료하는 패턴도 출력해야 한다. 패턴 중복을 동일 규칙으로 합칠지 구별할지 정한다.
- **반례:** 반복 문자열과 많은 접미 패턴에서는 `z`가 매우 커진다. 검색 전이만 선형이라고 결과 저장까지 작은 것은 아니다.
- **검산·연결:** 모든 패턴을 각각 내장 검색한 작은 결과와 비교한다. 패턴 목록이 바뀌면 자동자 버전을 갱신한다. [CMU 강의 자료](https://www.cs.cmu.edu/~cdm/resources/36-string-match.pdf)의 전이·실패 링크 설명을 참고한다.

## S06 — Rolling hash·Rabin–Karp

- **적용:** 여러 부분문자열 비교의 빠른 후보 검사. prefix hash는 전처리 `O(n)`, 정해진 산술 모형에서 구간 해시 계산 `O(1)`.
- **보장 경계:** 해시 일치는 문자열 동일성의 증명이 아니다. 정확성이 필수면 후보를 원문 비교로 확인한다. 두 해시를 써도 충돌 가능성이 사라지는 것은 아니다.
- **반례:** Python 기본 `hash()` 값을 영속 식별자로 쓰면 실행 간 안정성을 기대할 수 없다. 다른 길이·정규화 정책의 문자열을 같은 방식으로 비교하면 의미가 달라진다.
- **검산:** 원문 직접 비교와 대조하고 작은 modulus에서 의도적으로 충돌을 만들어 처리 경로를 확인한다. 콘텐츠 버전 식별용 암호학적 해시와 빠른 검색용 rolling hash의 용도를 구분한다.

## S07 — Suffix array·LCP·suffix tree

- **적용:** 변하지 않는 긴 본문에 많은 부분문자열 질의, 반복 구간, 공통 접두어. suffix array는 접미어 시작 위치를 정렬한 구조이고 LCP는 인접 접미어의 공통 길이를 기록한다.
- **비용:** 구축 방법에 따라 `O(n log² n)`, `O(n log n)`, 더 특수한 선형 방식까지 다르다. 단순 비교 이분 탐색 질의는 `O(m log n)` 수준이며 구현·보조 인덱스에 따라 달라진다. suffix tree의 이론적 선형 크기도 객체 기반 구현에서는 메모리 상수가 크다.
- **반례:** 각 접미어 문자열을 실제로 복사해 정렬하면 저장이 이차로 커질 수 있다. 본문 한 글자 변경에 기존 인덱스를 그대로 재사용하지 않는다.
- **검산:** 작은 본문의 모든 접미어를 직접 정렬한 결과와 검색 결과를 비교한다. [Princeton의 suffix array 자료](https://algs4.cs.princeton.edu/63suffix/SuffixArraysBook.pdf)를 구축·검색 개념의 참고로 사용한다.

## S08 — 편집 거리·유사도 후보

- **적용:** 오탈자 후보 순위, 텍스트 차이, 근접 중복 후보. 기본 Levenshtein DP는 두 길이 `n,m`에서 `O(nm)` 시간; 값만 구하면 행 두 개로 메모리를 줄일 수 있다.
- **조건:** 삽입·삭제·치환·전치 비용, 토큰/문자 단위, 길이 정규화와 임계값을 명시한다. 작은 편집 수만 필요하면 banded DP 등 조건부 가속을 검토한다.
- **반례:** 이름이 비슷하다고 같은 대상이라고 자동 병합하면 안 된다. 길이가 짧을수록 한 글자의 의미가 크며 업무상의 오류 비용은 단순 편집 수와 다를 수 있다.
- **검산·연결:** 실제로 허용한 편집을 작은 입력에서 열거하거나 별도 DP와 비교한다. 결과는 “동일”과 “검토 후보”를 구분한다. 임계값 선택이 누락/오탐을 바꾸면 사용자에게 그 절충을 설명한다.

## S09 — 정규식·유한 상태·파싱

- **적용:** 형식 검증, 토큰 추출, 반복 규칙. 실제 언어의 grammar가 있으면 parser 사용을 검토한다. [Python 정규식 문서](https://docs.python.org/3/library/re.html)에서 `search`, `match`, `fullmatch`와 문자 범위를 구분한다.
- **한계:** 모든 정규식 엔진과 문법이 선형 실행을 보장하지 않는다. 중첩 반복·복잡한 역참조는 실패 입력에서 많은 되돌림을 만들 수 있다. 괄호 중첩 같은 구조를 임의의 짧은 패턴으로 검증하지 않는다.
- **반례:** 전체 ID 형식을 확인하려는데 부분 일치만 검사하면 잘못된 앞뒤 문자가 통과한다. `\d`가 ASCII 숫자만 뜻하는지는 옵션과 엔진에 따라 확인한다.
- **검산·연결:** 정상·경계·아주 긴 불일치 입력을 검사한다. 시간 예산과 입력 길이 제한을 실제 서비스에 맞춘다. 파싱 실패를 빈 결과로 숨기지 않는다.

## S10 — 회문·압축·기타 조건부 선택

- **Manacher:** 모든 중심의 회문 반지름을 `O(n)`에 구하는 방법. 홀수/짝수 길이와 변환 인덱스의 원문 복원을 검산한다. 필요가 단순 한 문자열 회문 확인이면 양끝 비교가 더 단순하다.
- **Boyer–Moore 계열:** 패턴 오른쪽부터 비교해 건너뛰는 검색. 사용한 규칙·변형에 따라 최악 성능이 다르므로 이름만 보고 선형 보장을 붙이지 않는다.
- **Huffman·사전 압축:** 빈도나 반복성을 이용한 부호화. 저장/전송 목적일 때 데이터 포맷·호환·복구 비용을 함께 본다. 문자열 검색 인덱스와 다르다.
- **고급 선택지:** 동적 문자열 인덱스, suffix automaton, wavelet 구조는 반복 질의의 실제 병목과 요구 연산이 확인될 때 별도로 조사한다. 이 문서는 해당 구현을 포함하지 않는다.

## 실제 자료에서 먼저 결정할 것

공백·대소문자·Unicode 정규화가 업무적으로 허용되는지 먼저 판단한다. 정확 검색의 최적화와 유사 대상 판정은 다른 결정이다. 작은 자체 예시로 의미를 검산한 뒤 실제 입력 길이·패턴 수·출력 수를 측정한다. 외부 자료의 코드와 예문을 복사하지 않고 위 적용 사례를 작성했다.
