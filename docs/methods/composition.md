# 방법 조합과 서비스 연결

한 단계의 최적해가 전체 서비스의 최적해인 것은 아니다. 대상의 후보를 고르는 단계가 뒤의 선택지를 없애거나, 배정이 방문 순서와 소요시간을 바꾸면 각각의 계산 결과를 합치는 것만으로는 충분하지 않다. [목차](INDEX.md)에서 필요한 세부 방법을 고른 다음 실제 단계 사이의 의미를 확인한다.

## 단계별로 남길 정보

| 단계 | 전달할 값과 보장 | 흔한 실패 |
| --- | --- | --- |
| 입력·업무 의미 | ID, 단위, 날짜 기준, 참조 관계, 원본 버전 | 중복을 수요 증가로 계산, 실적을 전체 수요로 대체 |
| 후보 생성 | 허용 연결, 비용·거리의 출처, 제외 이유, 탐색 범위 | 가까운 몇 개만 남기고 원래 문제 전체가 불가능하다고 주장 |
| 선택·배정 | 각 대상의 선택, 자원 부하, 미처리, 목적값 | 그룹·정차 순서에 따라 비용이 바뀌는데 독립 비용으로 고정 |
| 순서·일정 | 실제 시각·순서, 방향별 이동, 시간·자원 점유 | 역방향이 같은 비용이라고 가정, 다음 날짜를 같은 날짜로 저장 |
| 개선·복구 | 변경 대상, 보존한 안정본, 현재 정책의 예외 범위 | 일부 지표 개선 때문에 다른 대상을 누락하거나 제약을 해제 |
| 전체 검증 | 원본 대상과 일치, 모든 필수 조건, 재계산한 지표 | 선택 함수가 반환한 점수·성공 문구를 그대로 신뢰 |
| 저장·표시 | 입력·설정·정책·코드 버전, 검증된 실행의 결과 | 옛 응답이 최신 설정의 결과를 덮어씀 |

각 단계는 실제 필요한 만큼만 분리한다. 새 추상 계층이나 플러그인 체계가 필요한 것은 아니다. 변할 수 있는 계산을 작은 함수로 분리하고 같은 함수가 실험과 실제 재계산에서 호출되게 하면 된다.

## 사례 1: 담당자와 작업 배정

입력은 담당자별 수행 가능 작업, 시간대, 작업량, 비용이다. 업무를 사람 하나에게 맡기는 선택이 핵심이면 [배정](assignment-flow.md)을 검토한다. 한 사람이 여러 업무를 맡고 소요시간이 다르면 단순 일대일 매칭 계약과 다르다. 방문 이동까지 있다면 배정 비용을 독립적으로 더할 수 있는지도 확인한다.

작은 흐름은 `자격·시간의 후보 확인 → 용량 있는 배정 → 실제 순서·이동 검증 → 충돌한 부분 재배정 → 전체 검증`이다. 순서가 비용과 실행 가능성을 바꾸면 이 단계를 반복하거나 [일정·경로 모델](routing-scheduling.md)로 함께 표현한다. 반복이 수렴하거나 최적이라는 보장은 별도 근거가 필요하다.

사용자에게는 “추가 작업을 맡기면 이동이 늘지만 필요한 담당자는 줄어듭니다. 합의한 지연 범위 안에서 인원을 줄일까요?”처럼 실제 절충을 보여준다. 필수 자격을 비용 벌점으로 바꾸어 무자격 배정을 허용하지 않는다.

## 사례 2: 예약과 장비 사용

입력은 요청 시작·종료, 장비 종류·수량, 준비 시간, 우선순위다. 겹침 여부는 [구간](ranges-and-time.md) 처리로 빠르게 알 수 있다. 그러나 장비별 가능 작업과 선후 관계가 얽히면 단순 구간 병합은 예약 배정 해법이 아니다.

같은 장비에 이어 붙일 수 있는 시각의 경계를 먼저 정한다. `[start, end)`에서 앞 작업 종료와 다음 시작이 같아도 준비 시간이 필요하면 실제 점유 구간을 확장해야 한다. 삭제·시간 변경 시 이전 결과를 증분 수정하는 방법과 전체 재계산의 결과를 작은 사례에서 비교한다.

동일한 설정과 유효한 입력에 대해서도 계산 이후 다른 요청이 저장될 수 있다. 계산 함수의 정답과 저장 시점의 경합 처리는 별도 책임이다. [웹 상태 점검](../../.agents/skills/double-loop-solver/references/web-state-checks.md)의 실제 기능 관련 사례를 적용한다.

## 사례 3: 거점 선택과 방문 경로

입력은 위치, 수요, 허용 거점, 이동 자료, 용량이다. [공간 인덱스](spatial-grouping.md)는 근처 후보 검색을 줄이고 [시설 선택](optimization-models.md)은 열 거점을 정하며 [경로](routing-scheduling.md)는 방문 순서를 만든다. 군집의 중심이 실제 선택 가능한 위치인지 확인한다.

후보 수를 줄이면 계산이 쉬워지지만 좋은 해나 유일한 유효 해를 잃을 수 있다. 후보 수를 늘렸을 때 처리 범위가 회복되는지 확인하고, 거리 하한 등으로 증명한 제거와 임의의 가까운 후보 제한을 구별한다. 위경도 거리·도로망 비용·실측 이동시간은 서로 다르다.

경로별 최소 이용률 같은 사용자가 추가한 기준이 전체 처리를 막으면 [승인된 정책 안의 회복](../../.agents/skills/double-loop-solver/references/baseline-and-delivery.md)을 검토한다. 현재 구성원과 설정으로 예외 대상을 자동 선정하며 이름·과거 그룹 ID를 고정하지 않는다. 이는 계산 방법 변경과 정책 변경의 효과를 함께 기록해야 하는 사례다.

## 분리 가능한지 확인할 질문

- 사업장·날짜·그룹별로 나눌 때 공유하는 인력·장비·예산·재고가 없는가?
- 오늘의 선택이 다음 날 상태를 바꾸는가? 자정 경계나 연속 작업이 잘리는가?
- 후보 단계에서 잃은 연결을 다음 단계가 복구할 수 있는가?
- 거리나 비용이 순서·동시 배정·혼잡에 따라 바뀌는가?
- 묶음별 최적을 합치면 전체 공정성·최대 부담·자원 제한도 지키는가?

답에 따라 분할의 정당성을 확인하거나 공동 제약과 경계 상태를 전달한다. 서로 독립임을 확인하지 않고 단순히 워커 수만큼 데이터를 나눠 최적화하지 않는다.

## 비교와 전달

[후보 비교 양식](../../templates/candidate-comparison.md)에 필요하면 `후보 생성 → 배정 → 순서 → 복구`의 변경 단계와 인터페이스를 한 줄로 추가한다. 같은 입력·설정·정책에서 한 단계만 바꿨는지, 여러 단계를 함께 바꿔 원인을 분리하지 못했는지 밝힌다. 채택한 조합은 실제 서비스 경로에서 새 입력·설정과 함께 재실행한다.

사용자에게는 구성 요소 전부의 구현 승인을 요구하지 않는다. 이미 정한 기준의 기술 선택은 진행하고, 목표·현실 근사·중요한 운영 절충만 추천안과 근거를 보여준다. 워커는 기존 완료 주장 대신 현재 기준의 실행 증거를 반환한다.
